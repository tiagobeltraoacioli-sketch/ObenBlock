# OBIP-6: Commit-reveal votes in the vote window

```
  OBIP: 6
  Layer: Consensus (hard fork)
  Title: Commit-reveal votes in the vote window
  Author: gnb-smh <gnb-smh@proton.me>
  Status: Draft
  Type: Standards Track
  Created: 2026-10-18
  License: BSD-2-Clause
  Requires: none
```

## Abstract

This OBIP adds an optional two-phase form of the PoCI finality vote. A
witness first gets a signed commitment to its vote included on chain. Later
it reveals the ordinary v3 attestation and a salt. Both phases fit inside the
base vote lifetime: `vote_ttl` = 720 blocks, which is 12 checkpoints of 60
blocks, or 6 hours. No PoCI invariant changes. Plain votes remain valid, and
each witness chooses for itself. The node's witness duty defaults to plain
votes. The rule is not scheduled for activation until regtest measurements
show its cost.

## Motivation

In the base, a vote's content is public from the moment it is gossiped. The
content is its source and target hashes under a named configuration. Two
behaviours depend on seeing that content early:

- **Content-selective inclusion.** A block producer can decide whether to
  include a vote based on which branch or source it supports, before any
  other miner has a chance to include it.
- **Wait-and-see voting.** A witness can hold back until it sees which link
  is gathering weight, and then follow it without checking the data itself.
  The technical note's model has each voter verify independently (pp. 10–11).
  That model assumes votes are decided independently.

A commit phase hides the content until the commitments are fixed on chain.
The gain is limited, as Security Considerations explains. The base
producer rule (vote for the justified checkpoint's direct child) makes most
honest votes predictable from the chain anyway. That is why this OBIP is
optional, off by default, and gated on measurement.

## Specification

### Phases

For a target checkpoint `t`, a vote is includable in the base at heights `h`
with `t.height < h <= t.height + vote_ttl`. This OBIP splits that range in
two:

```text
commit phase  : t.height < h <= t.height + commit_len
reveal phase  : t.height + commit_len < h <= t.height + vote_ttl
constraint    : 0 < commit_len < vote_ttl                       (vote_ttl = 720)
```

- OPEN: `commit_len`. Values to measure: 60, 180 and 360 blocks. Each is a
  whole number of checkpoint intervals.
- Both phases stay within `vote_ttl`, so the base invariants
  `vote_ttl <= epoch_len` and `vote_ttl + checkpoint_interval < 2 *
  epoch_len` (CONSENSUS.md "PoWit", `params_keep_the_frozen_window`) still
  hold. The frozen-window reasoning of the base is unchanged.

### Commitment (body item, commit phase)

```text
c        = SHA3-256( u32le(17) ‖ "OBB-OBIP6-v1/hide" ‖ msg_v3 ‖ salt[32] )
msg_c    = SHA3-256( u32le(19) ‖ "OBB-OBIP6-v1/commit" ‖ u32le(chain_id)
                     ‖ config_id[32] ‖ u8(depth) ‖ root[32]
                     ‖ u64le(target.height) ‖ c[32] )
commit   = (depth, root, config_id, target.height, c, kes_sig over msg_c)
```

- `msg_v3` is the vote's base attestation message (DESIGN-obenblock-poci.md
  §2). It commits the KES key, the configuration and the link.
- The configuration, the key and the target height are public. The source,
  its height and the target hash are hidden. The target height is a slot
  number, so it reveals nothing about content.
- Signing uses the KES leaf of `epoch(target.height)`, as for the vote.
- A commitment is valid only if:
  - the key is an entry of the named configuration;
  - `target.height` is a checkpoint slot;
  - the block is in the commit phase of that slot;
  - no commitment by the same key for the same `(config_id, target.height)`
    is already on the selected chain. The first one included wins, and a
    second one makes the block invalid.

### Reveal (body item, reveal phase)

```text
reveal = (attestation v3 wire, salt[32])
```

A reveal is valid only if:
- the attestation passes every base check;
- a commitment by the same key for the same `(config_id, target.height)` is
  on the selected chain;
- its `c` equals the hash of this attestation's `msg_v3` and `salt`;
- the block is in the reveal phase.

A valid reveal counts exactly like a base attestation:
- the registry weight of the named configuration;
- once per key per link;
- the strict quorum of DESIGN-obenblock-poci.md §3.

### Interaction with plain votes and evidence

- A key may vote plainly for a slot, or commit and reveal. It still counts at
  most once per link.
- A plain vote and a revealed vote that conflict are both signed
  attestations. They are ordinary double-vote or surround-vote evidence
  (DESIGN-obenblock-poci.md §5).
- **Commitments are never evidence.** An unrevealed commitment is not
  punished. Not revealing is abstention, and absence is never punished in
  PoCI.
- A commitment cannot be used to prove a conflict, because its content is
  hidden.
- OPEN: whether a revealed attestation is also accepted as evidence when its
  commitment was on a branch that lost. It is a signed attestation, so the
  base rules already admit it.

### Signer protection

The base signer rules (DESIGN-obenblock-poci.md §8) are extended:

- The vote record stores the full vote and the salt. A committed vote counts
  as cast for the double-vote and surround-vote refusal, even before its
  reveal. Only one commitment per `(key, config_id, target.height)` is ever
  signed.
- The salt is 32 bytes from the OS CSPRNG. It is written and fsynced before
  the commitment signature leaves the process.
- A crash that loses the salt only forfeits the reveal. That is abstention,
  and it is safe.

### Activation and opt-in

- **Consensus support** is a hard fork at a coordinated release height. OPEN:
  the height. It is not scheduled until the regtest measurements
  (Deployment prerequisites) are published.
- `commit_len` and the commit-reveal version enter `params_digest`, which
  needs a new digest version.
- **Use is per witness.** The witness duty and `gnb-cli powitattest` default
  to plain votes. Commit-reveal is enabled with an explicit option. OPEN: the
  option names.

### Parameters

- OPEN: `commit_len`.
- OPEN: per-block limits for commitments and reveals. They share the base
  budget of 32 attestations, or the OBIP-5 budgets if that OBIP is
  activated.

## Rationale

- **Inside the current window.** A longer window would change `vote_ttl`.
  It would also break the invariants that let the base keep only `window +
  2` epochs plus the frozen window. Splitting the 6 hours keeps every base
  bound as it is.
- **Signed commitments rather than unsigned ones.** With unsigned
  commitments under a "first one wins" rule, anyone could block a key by
  committing junk in its name first. Allowing many unsigned commitments per
  key instead invites spam. A KES signature costs one more hybrid signature
  per vote (about 4.6 kB). That cost is the main thing to measure.
- **Blind voting rejected** (base). Blind signatures or anonymous credentials
  hide who voted. That conflicts with weight checking and with Proof of
  Corruption, both of which need the key.
- **Receipt-free voting rejected** (base). A reveal is a receipt: anyone can
  check what a key voted. This OBIP does not try to stop bribery or
  coercion. Receipt-freeness would need trusted tallying or heavy
  cryptography, and the base rejects it.
- **Threshold or timelock encryption of votes** would hide content without a
  second inclusion. It needs a decryption committee, which is a new trust
  assumption, or a time-lock puzzle whose delay depends on hardware. Neither
  fits a stakeless, work-weighted set.
- **A random multi-round committee and a local committee change** are not
  needed. Commit-reveal does not change who votes or their weights.

## Backwards Compatibility

- This is a hard fork. Commitment and reveal items are invalid under the base
  rules.
- Plain votes stay valid and keep their meaning.
- Activation is a coordinated ObenBlock release height, preferably the
  opening checkpoint of an epoch, so the new `params_digest` takes effect at
  a handoff.
- GnB is unaffected.

## Security Considerations

**What it prevents, within limits:**
- Content-selective inclusion during the commit phase. A producer sees only
  the key and the slot.
- Wait-and-see voting during the commit phase. Commitments are fixed before
  any committed content is public.

**What it does not prevent:**
- **Censorship by key.** The key is public at commit time.
- **Censorship by content in the reveal phase.** Reveals are public. A miner
  can still drop a reveal. Other miners can include it until `t.height +
  vote_ttl`.
- **Predictable votes.** Honest votes follow the base producer rule, so
  their content can usually be guessed from the chain. Hiding it adds little
  for honest witnesses.
- **Bribery and coercion.** The reveal is a receipt.
- **Lazy validation.** A witness can commit without checking the data.
- **Equivocation.** More than 1/3 equivocating weight still breaks safety,
  with evidence. Commit-reveal does not change accountable safety.
- **Partitions** and a missing quorum.
- **Selective reveal.** A key that committed can choose not to reveal, which
  is abstention. A key cannot commit twice for one slot, so it cannot pick
  between two committed contents.

**Liveness cost:**
- Justification of `t` cannot happen before height `t.height + commit_len +
  1`.
- Each vote needs two inclusions, so with the base limit of 32 the inclusion
  bound becomes `2 × ceil(K/32)` blocks.
- Sustained capacity also halves. A 60-block interval has 1,920
  attestation slots. Plain votes keep one link per checkpoint up to
  `K = 1,920`. Commit-reveal does so only up to `K = 960`. Above that,
  finality falls behind the checkpoints. OBIP-5 removes this limit, but this
  OBIP does not require it.
- Finality latency grows by at least `commit_len` blocks per link.

**Assumptions:**
- SHA3-256 hiding and binding with a 32-byte random salt.
- The base PoCI assumptions.

**Post-quantum status:**
- The commitment is hash-based, and both signatures are KES with hybrid
  ML-DSA-65 + Falcon-1024 (about 4.6 kB each).
- No pairing SNARK, BLS or Groth16 is used.

## Deployment prerequisites

Regtest measurements for each `commit_len` candidate, against plain votes, at
`K` of 64, 640 and 1,920:
- bytes per vote;
- blocks from target to justification and to finality, p50/p95/p99;
- the share of reveals that miss the deadline under induced delay and under
  a censoring miner with 1/3 of the hashrate;
- verification time per block.

Also needed:
- a reference model with vectors next to `reference/poci_reference.py` (branch `obenblock/o11a-poci-reference`);
- a decision by the owner that the measured gain justifies the cost.
