# OBIP-1: OBIP purpose and process

```
  OBIP: 1
  Layer: Process
  Title: OBIP purpose and process
  Author: gnb-smh <gnb-smh@proton.me>
  Status: Active
  Type: Process
  Created: 2026-10-18
  License: BSD-2-Clause
  Requires: none
```

## Abstract

An ObenBlock Improvement Proposal (OBIP) is a design document that proposes
a **future** change to ObenBlock: a consensus rule, a peer-to-peer message, an
RPC, an application convention or a process. This OBIP defines what an OBIP
is for, the sections it must contain, how it moves from Draft to Final, who
edits the series, how numbers are assigned and how a consensus OBIP is
activated on ObenBlock. It is adapted from Bitcoin's BIP-2
(https://github.com/bitcoin/bips/blob/master/bip-0002.mediawiki).

## Motivation

ObenBlock already has a written base specification. The relaunch is
implemented on branches and specified in these documents:

- `docs/DESIGN-obenblock.md`: SHA-256d proof of work (§4), chain identity and
  `obb` addresses (§2), genesis (§3), stall relief (§5.1), witness shares and
  the long window (§6.1, §6.2), the growth cap on W (§6.3), advisory Bloch
  anchors (§8 phase 1);
- `docs/DESIGN-obenblock-poci.md`: PoCI strict finality, frozen
  configurations and handoff (§2–§4), absence pruning by the old committee
  (§4.1), Proof of Corruption and the 100-epoch ban (§5), the finality
  certificate (§6), signer protection (§8), launch (§9);
- `docs/CONSENSUS.md`, section "PoWit": messages, witness set, the bound of 32
  attestations per block and `ceil(K/32)` blocks of inclusion;
- `docs/DESIGN-witness-shares.md`: share rewards, slots and window;
- `docs/BLOCH-ANCHOR.md`: BLA1 anchors of Bloch checkpoints in ObenBlock.

That base is **not** restated as OBIPs. OBIPs exist for what comes next, so
that each evolution is argued, reviewed and activated on its own, with a
stable reference to the exact base text it changes. Without a process,
proposals arrive as chat messages, notes or pull requests with no common
shape, no record of rejected alternatives, and no shared rule for when a
consensus change may activate.

## Specification

### What an OBIP is, and what it is not

- An OBIP proposes one coherent change on top of the base specification, or
  on top of other Final OBIPs. It cites the base by document and section
  (for example "DESIGN-obenblock-poci.md §4.1"), never by paraphrase alone.
- An OBIP is not an implementation report, not an audit, and not a claim that
  a research question is solved. An OBIP that depends on open research says
  so and marks every undecided parameter as `OPEN: …`. Inventing a value to
  fill a field is a reason for an editor to return the draft.
- Bug fixes that restore the behavior the base specification already
  describes do not need an OBIP. Changes to that behavior do.

### Types

- **Standards Track**: changes a rule or interface that implementations must
  agree on (consensus, peer services, API/RPC, application conventions).
- **Informational**: describes a design issue or gives guidance, without
  proposing a rule. Implementers may ignore it.
- **Process**: changes how the project decides or works (like this OBIP).
  Process OBIPs are binding on the process once Active.

### Layers

Every Standards Track OBIP names exactly one layer:

| Layer | Scope |
| --- | --- |
| Consensus (hard fork) | blocks or transactions valid under the new rules were invalid under the old ones; every node must upgrade before the activation height |
| Consensus (soft fork) | the new rules only restrict what was valid; old nodes keep following the chain |
| Peer Services | P2P messages, relay, wire objects that are not consensus |
| API/RPC | node RPC, CLI and their outputs |
| Applications | wallets, daemons, registries on other chains, conventions above the node |
| Process | process OBIPs (Type Process) |

An Informational OBIP names the layer it concerns; a Process OBIP names
Process.

A proposal that spans layers names the layer of its strictest part and
describes the other parts in its Specification. If the parts can be adopted
separately, the editors may ask for a split.

### Preamble

Each OBIP starts with a fenced preamble, in this order:

```
  OBIP: <number>
  Layer: <one of the layers above>
  Title: <at most 44 characters>
  Author: <name> <<email>>[, …]
  Status: <status>
  Type: Standards Track | Informational | Process
  Created: <YYYY-MM-DD>
  License: BSD-2-Clause
  Requires: <OBIP numbers, or none>  (technical dependencies only;
                                      OBIP-1 is implied and not listed)
  Replaces: <OBIP number>            (optional)
  Superseded-By: <OBIP number>       (optional)
```

### Required sections

1. **Abstract**: about 200 words.
2. **Motivation**: the problem, with a reference to the base text where it
   arises.
3. **Specification**: byte-level where the change defines encodings, integer
   arithmetic where it defines weights or thresholds; undecided points as
   `OPEN: …`.
4. **Rationale**: why this design, the alternatives considered, and the
   alternatives already rejected for the base (for example merged mining,
   stake bonds, local committee change, random multi-round recomposition,
   blind or receipt-free voting, self-anchoring) where they are relevant.
5. **Backwards Compatibility**: what old nodes and wallets see, and how the
   change activates. GnB is a separate chain and must be stated as unaffected
   or the effect described.
6. **Reference Implementation**: link to the branch and reference model, or
   "none yet".
7. **Test Vectors**: link to the vector files, or "pending".
8. **Security Considerations**: every assumption stated honestly, including
   classical and quantum assumptions of each cryptographic layer.
9. **Deployment prerequisites**: what must exist before the OBIP may become
   Proposed (measurements, other OBIPs, access to other code bases).
10. **Copyright**.

A Consensus OBIP without a byte-level Specification, a reference model and
test vectors cannot leave Draft.

### Files and numbering

- File: `docs/obip/obip-NNNN.md`, the number padded to four digits, English
  only. Supporting files go in `docs/obip/obip-NNNN/`.
- Numbers are assigned by an editor, in order, when a draft is accepted into
  the repository. Authors do not self-assign. A number is never reused, even
  for a Rejected or Withdrawn OBIP.
- OBIP-1 is this document.

### Workflow and statuses

```
Draft ──> Proposed ──> Final
  │           │
  ├──> Withdrawn (by the author)
  ├──> Deferred  (no progress; may return to Draft)
  └──> Rejected  (by the editors, with the reason recorded)

Process / Informational:  Draft ──> Active
Final or Active ──> Replaced (Superseded-By names the successor)
```

- **Draft**: under discussion; may change freely.
- **Proposed**: the specification is complete, there is a reference
  implementation and test vectors, and the review below has passed. Changes
  are limited to errata found during implementation.
- **Final**: for a consensus OBIP, the rules are active on mainnet at the
  activation height and shipped in a release; for other layers, at least one
  released implementation follows it.
- **Active**: a Process or Informational OBIP in force.
- **Deferred**: the author asks to pause, or there has been no progress for
  a period set by the editors (OPEN: that period).
- **Rejected**: the editors decide it should not proceed; the reason and the
  date are added to the document.
- **Withdrawn**: the author stops it.
- **Replaced**: a later OBIP supersedes it.

### Review

Before an OBIP becomes Proposed it passes the audit process already used for
the base (`docs/DESIGN-obenblock.md` §9; `docs/security/round-2/README.md`):

1. **Reproduce first**: a test or simulation that shows the problem the OBIP
   solves, which fails without the change and passes with it.
2. **Reference and vectors**: an executable reference model (Python, integer
   arithmetic, run with `python3 -I`) that writes the vectors and checks them
   (`--check` in CI), with acceptance and rejection cases.
3. **Three-lens review**: three reviewers independent of the implementation
   check, separately, (a) semantics against the specification, (b) input
   paths and resource bounds, and (c) test strength (the tests fail when the
   change is reversed).
4. Full test suites and a draft pull request.

### Activation of consensus OBIPs

- **Regtest first.** The rules are implemented behind an activation height
  that regtest sets to 0 (or to a test height), and run there, including the
  reference vectors and the partition simulations where finality is
  affected. ObenBlock has no public testnet (`DESIGN-obenblock.md` §1).
- **Coordinated release height.** Mainnet activation is a height fixed in a
  release, never signalled by miners. The height is chosen as in the base
  activation record (`docs/security/round-1/README.md`, "Activation 2
  decision record"): a fresh reading of the live tip from more than one
  independent node, the greater of that tip and the ASERT schedule height,
  plus an update window agreed in the OBIP, rounded up to an epoch boundary
  (720 blocks). A candidate height that has become too close is not reused.
- **Finality-affecting rules** activate at an epoch boundary and enter into
  force through a PoCI handoff (`DESIGN-obenblock-poci.md` §4), so that one
  configuration never mixes old and new rules. A change of any parameter in
  `params_digest` (`DESIGN-obenblock-poci.md` §2) changes every `config_id`
  from the first configuration under the new rules.
- **No silent change below the height.** Every verdict below the activation
  height stays bit-identical; producers must emit valid output at `H-1` and
  `H`.
- **GnB is unaffected** by ObenBlock activations. Chain ids keep the chains
  apart (`DESIGN-obenblock.md` §2).

### Editors

- The editors check form, assign numbers, merge drafts and record status
  changes. They do not judge the merit of a proposal beyond the requirements
  of this OBIP, except when rejecting one, with the reason written down.
- The first editor is the project owner (gnb-smh). OPEN: further editors and
  how they are appointed.

### Comments

- Discussion takes place in the pull request that adds or changes the OBIP,
  and in the repository's issue tracker. A summary of objections and how they
  were handled goes in the Rationale before the OBIP becomes Proposed.
- OPEN: a mailing list or forum for OBIP discussion.

## Rationale

- **BIP-2 as the base.** It is well known to Bitcoin developers, whose ASICs
  ObenBlock uses, and it separates proposal, review and activation.
- **Differences from BIP-2.** Activation is a coordinated release height
  (ObenBlock has no miner signalling, and the base itself activated that
  way); a consensus OBIP must carry a reference model and vectors before
  Proposed, as the audit process requires for the base; the base
  specification is cited, not rewritten as OBIPs.
- **Rejected: an OBIP per base feature.** Rewriting the base as OBIPs would
  duplicate documents that are already reviewed and would invite the two
  texts to drift.
- **Rejected: miner signalling (BIP-9 style).** Signalling gives hashrate a
  veto over changes; on ObenBlock hashrate can be rented
  (`DESIGN-obenblock.md` §6.3), so it is a weak governance signal.

## Backwards Compatibility

This OBIP changes no rule. GnB is unaffected.

## Test Vectors

Not applicable.

## Security Considerations

The process does not make a proposal secure. It makes its assumptions
written and reviewable. The activation rule assumes that operators upgrade
within the update window; a node that has not upgraded by a hard-fork height
follows the old rules and leaves the network.
