## Abstract

PoCI counts finality weight per KES key (DESIGN-obenblock-poci.md §2), but
its safety assumption is about **independent control**: less than one third
of the weight of a configuration may be Byzantine. A thousand keys run by
one operator, one pool, one hosting provider or one software build are one
failure domain. This OBIP describes how a node can report, from data it
already has, how concentrated the weight of a configuration is across
effective operators, payout pools, network providers and software. It
defines an RPC (`getoperatordiversity`), metric names and the clustering
signals, each with its reliability. The metrics are **observational only**:
they never change weights, eligibility, quorum, fork choice, templates or
relay. They are lower bounds on concentration: links the node can observe
merge keys; an operator who hides its links looks more diverse than it is,
and the report says so.

## Motivation

- The technical note behind PoCI (section on corruption and keys) recommends
  measuring weight per effective operator, pool, provider and software,
  because key counts say nothing about independent control.
- The growth cap (DESIGN-obenblock.md §6.3) makes capture slow and visible
  through `getpowitinfo` (`sum(x)`, `G_e`, admitted share of new keys). It
  does not show whether existing weight is already concentrated.
- Absence pruning (DESIGN-obenblock-poci.md §4.1) and the no-quorum halt
  (§7) mean that a single operator above one third of `C_e` can halt
  finality by going offline. Operators and exchanges should see that number.
- Block production concentration (pools) is a separate risk from finality
  concentration and should be reported separately.

## Specification

Nothing in this section is a consensus rule. A node implementing it must not
read any of its outputs in validation, fork choice, the witness duty,
templates, relay or peer scoring.

### Inputs

For a configuration `C_e` (DESIGN-obenblock-poci.md §2), the node uses:

1. `entries_e`: `(key_id, weight)` and `total_e`, from finalized history.
2. Share payouts: the payout script of every witness share credited to each
   key in the window (DESIGN-witness-shares.md, "What it rewards": `witness`
   and `payout` are separate fields of the share).
3. Co-spending of share payouts in later finalized transactions
   (common-input ownership).
4. Node-local network observations: for each key, the peers from which the
   node first received that key's attestations, with the peer's address and
   advertised user agent.
5. Optional operator declarations (below).

### Clustering signals

| Signal | Links keys `a`, `b` when | Reliability |
| --- | --- | --- |
| `payout` | some share of `a` and some share of `b` pay the same payout script | strong evidence of a shared beneficiary; trivially avoidable by using distinct scripts |
| `cospend` | outputs paid to payouts of `a` and `b` are inputs of one finalized transaction | heuristic; coinjoin-like transactions create false links |
| `declared` | both keys appear in one valid operator declaration | self-reported; only links, never splits |
| `asn` | first-relay peers of both keys map to the same autonomous system | node-local, needs an operator-supplied IP-to-ASN table; relays are not originators |
| `software` | first-relay peers advertise the same user agent | node-local, self-reported by peers |

- **Effective operator** clusters: the connected components of the graph
  whose edges are `payout`, `cospend` and `declared` links (OPEN: whether
  `cospend` is on by default).
- **Provider** clusters: components of the `asn` relation.
- **Software** clusters: the user-agent string of the first-relay peer,
  normalized to name and major version (OPEN: normalization).
- A key with no link is its own cluster. Unobserved keys (no relayed vote
  seen by this node) are reported as `unknown` for the node-local signals.

### Operator declaration (optional)

An operator may link its keys voluntarily:

```text
decl_msg = SHA3-256( u32le(17) ‖ "OBB-OPDECL-v1/msg" ‖ u32le(chain_id)
                     ‖ u64le(epoch) ‖ u32le(n) ‖ key_id_0[20] ‖ … ‖ key_id_{n-1}[20]
                     ‖ u16le(len) ‖ label[len] )
```

signed by the KES leaf of `epoch` of every listed key (OPEN: whether one
signature per key is required, or the encoding is final). Key ids are
strictly ascending. Declarations travel by RPC (`submitoperatordeclaration`)
and are stored locally; they are not gossiped by consensus code and never
included in blocks (OPEN: an optional relay item). A declaration can only
merge clusters. It is not evidence of anything and is never used against a
key.

### Metrics per partition (operator, provider, software)

For the cluster weights `w_1 >= w_2 >= …` of `C_e` with total `T`:

- `nakamoto_third`: the smallest number of clusters whose weight `w` satisfies
  `3 w >= T` (enough to halt PoCI finality by going offline, §7).
- `nakamoto_strict_third`: the smallest number with `3 w > T` (enough, if
  they equivocate, to make two conflicting quorums possible; §3).
- `nakamoto_two_thirds`: the smallest number with `3 w > 2 T` (enough to
  finalize alone).
- `hhi_ppm`: `floor(10^6 × Σ w_i² / T²)` (Herfindahl-Hirschman index, parts
  per million), integer arithmetic.
- `top`: the 10 heaviest clusters with weight in basis points
  (`floor(10^4 × w_i / T)`) and their keys (OPEN: count).

Block production uses the same metrics over the selected-chain blocks of the
last window, weighted by block count, clustered by coinbase output script and
by pool tag (the free bytes after the coinbase prefix, CONSENSUS.md
"Coinbase commitment"; OPEN: tag parsing).

### RPC

`getoperatordiversity [epoch] [signals]` returns, for the configuration in
force (or the named past one):

```json
{
  "epoch": 4421,
  "config_id": "…",
  "total": "…",
  "keys": 312,
  "partitions": {
    "operator": { "clusters": 0, "nakamoto_third": 0, "nakamoto_strict_third": 0,
                  "nakamoto_two_thirds": 0, "hhi_ppm": 0, "top": [], "signals": ["payout", "declared"] },
    "provider": { "…": "…", "observed_weight_bp": 0 },
    "software": { "…": "…", "observed_weight_bp": 0 }
  },
  "blocks": { "window_blocks": 0, "nakamoto_half": 0, "hhi_ppm": 0, "top": [] },
  "lower_bound": true
}
```

(Values above are placeholders, not measurements.) `lower_bound` is always
`true`. `observed_weight_bp` is the share of `total` for which the node saw
the node-local signal.

### Prometheus metrics

`obb_diversity_nakamoto_third{partition}`,
`obb_diversity_nakamoto_strict_third{partition}`,
`obb_diversity_hhi_ppm{partition}`,
`obb_diversity_top_bp{partition}` (OPEN: prefix; the base uses `gnb_` names
such as `gnb_deep_reorgs_total`, DESIGN-obenblock.md §7).

### Privacy

The `asn` and `software` signals reveal what the node observed about its
peers. They are off by default in the RPC (`signals` must name them) and not
exported to Prometheus unless enabled (OPEN: defaults).

## Rationale

- **No consensus effect.** Every signal is either avoidable (payouts),
  self-reported (declarations, user agents) or node-local (network). Using
  them in weights would let an attacker split itself to look diverse or
  frame honest keys as linked. Reporting them is safe; acting on them in
  consensus is not.
- **Lower bound, stated.** A cluster count is an upper bound on the number
  of independent operators only for the links seen. The RPC flags this so
  that dashboards do not present it as proof of decentralization.
- **Three thresholds.** One third (halt), strictly more than one third
  (conflicting quorums) and strictly more than two thirds (sole control)
  match PoCI's quorum rule (DESIGN-obenblock-poci.md §3) exactly.
- **Stake bonds or identity registries** to enforce diversity were rejected
  for the base (DESIGN-obenblock.md §1: share work only, no stake) and
  would add a trusted identity layer.
- **Per-operator caps in the weight function** (local committee change by
  observed identity) are rejected: identity is not observable, and a cap
  based on it changes `C_e` by local judgement, which the base forbids
  (DESIGN-obenblock-poci.md §2, §4).

## Security Considerations

- **Sybil hiding.** An operator controlling more than a third through many
  unlinked keys and payouts shows up as many small clusters. The metric
  cannot detect it; only its absence of links is reported.
- **Framing.** Anyone can pay to someone else's payout script or co-spend
  coins to create `cospend` links. Since the metrics have no effect on
  consensus, framing can only mislead readers; reports should name the
  signals that created each link.
- **Node-local signals are partial.** The first-relay peer is often a
  relay, not the operator; eclipse attacks can feed a node false user
  agents and addresses.
- **Cryptography.** Declarations use the KES keys of PoWit (hybrid
  post-quantum signatures, about 4.6 kB each); no new primitive.
- **Resource use.** Clustering over the window's shares and payouts must be
  bounded (computed per handoff and cached).

## Deployment prerequisites

- A decision on the default signals and the privacy defaults.
- An operator-supplied IP-to-ASN source format (none is shipped).
- Agreement on metric names with the existing `gnb_` metrics.
