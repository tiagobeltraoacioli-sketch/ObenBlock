## Abstract

This OBIP proposes succinct validity proofs of block execution for
ObenBlock. Every selected-chain block commits to the UTXO-set state of its
selected parent; any party (a *prover*) may then publish a proof that
applying the block's body to that state under the ledger rules yields the
next committed state. PoCI voters and other nodes may verify the proof
instead of re-executing the block. The proof is **separate from finality**:
PoCI certificates (DESIGN-obenblock-poci.md §6) keep their meaning, finality
never waits for a proof, and a valid proof never makes a block final. The
consensus part is a soft fork (a new mandatory state commitment inside the
coinbase's free bytes); proofs themselves are a peer-services object in the
first phase. The post-quantum path is a hash-based transparent proof
(STARK family), whose proofs are tens to hundreds of kB; classical pairing
SNARKs (Groth16) are used only as a laboratory baseline because they are not
post-quantum. Proof system, circuit, accumulator, prover incentives and
every cost figure are open and must be measured before this OBIP can leave
Draft.

## Motivation

- Today every full node and every PoCI voter must re-execute every
  selected-chain block (CONSENSUS.md "Ledger semantics: selected-chain-only")
  to know that a checkpoint it votes for is valid. Signature verification of
  the hybrid ML-DSA-65 + Falcon-1024 witnesses (CONSENSUS.md "Witnesses") is
  the dominant cost, and it grows with the block size limit
  (CONSENSUS.md "Block size (VAL-12)", 1,000,000 bytes).
- Sampling does not replace execution. The technical note behind PoCI
  (P1 items) computes that sampling 32 of 1,000,000 transactions lets one
  invalid transaction pass with about 99.9968 % probability. Witness shares
  (DESIGN-obenblock.md §6.1, DESIGN-witness-shares.md) prove custody of
  block data, not validity of the block.
- A validity proof lets a verifier check the whole state transition at a
  cost independent of the block's content, which is a prerequisite for
  lighter voters, for faster initial sync, and for a settlement layer
  (OBIP-13).
- ObenBlock's header (DESIGN-obenblock.md §4.1) carries no state commitment,
  so there is nothing today a proof could be bound to.

## Specification

### Terms

- `S(B)`: the UTXO set after applying the selected chain from genesis up to
  and including block `B` (CONSENSUS.md "Ledger semantics").
- `SC(B)`: a 32-byte commitment to `S(B)` under an accumulator `ACC`.
- `rules_id`: a 32-byte digest of the ledger rules the proof covers (OPEN:
  exact preimage; it must at least commit the chain id of
  DESIGN-obenblock.md §2 and the activation height of this OBIP).

### State commitment (consensus, soft fork)

From the activation height `H_VP`:

1. Every block `B` with `height(B) >= H_VP` carries `SC(sp(B))`, the
   commitment to the state **after its selected parent**, in the coinbase
   `script_sig`, directly after the 80-byte prefix of CONSENSUS.md
   "Coinbase commitment (VAL-2 BIP34, CRY-1)":

   ```text
   offset size field
    80      8   "OBB-SC01"                          (tag; OPEN: final tag)
    88     32   SC(sp(B))
   ```

   This uses 40 of the 9,920 bytes the base leaves to the miner, so it only
   restricts what was valid (soft fork). The commitment is covered by the
   block id through `merkle_root` exactly as the base prefix is.
   OPEN: a common layout for tagged OBIP fields in the coinbase miner
   bytes (OBIP-9 `OBB-DA01`, OBIP-10 `OBB-SC01`, and pool tags read by
   OBIP-11), so that both fields can be present; the offsets shown assume
   this field is the only one.
2. A block whose `SC(sp(B))` does not equal the node's own computation of
   the accumulator over `S(sp(B))` is invalid.
3. A block commits to its selected parent's state, not its own, because the
   coinbase is part of `S(B)` and cannot commit to itself (the same reason
   the base witness root puts 32 zero bytes at position 0).

`ACC` (OPEN): a hash-based accumulator over canonical UTXO entries
(outpoint, value, script, height, coinbase flag), with deterministic
insertion and deletion in block order. Candidates: a sorted Merkle tree or
sparse Merkle tree with the repo's tagged-hash construction; a hash-based
forest (Utreexo style). Multiplicative-group set hashes (MuHash) are
excluded because their collision resistance rests on discrete logarithms and
is not post-quantum. The update cost per block and the proof cost of `ACC`
inside the circuit must be measured.

### The proven relation

A validity proof `π(B)` for a selected-chain block `B` proves knowledge of a
witness such that, with public inputs

```text
public = ( u32le(chain_id), rules_id[32], block_id(B)[32],
           SC(sp(B))[32], SC(B)[32] )
```

the following holds:

- the block body hashes to the `merkle_root` and `witness_root` committed by
  `block_id(B)` (DESIGN-obenblock.md §4.1; CONSENSUS.md "Coinbase
  commitment");
- every transaction of `B` is valid against `S(sp(B))` and the transactions
  before it in `B`: value ranges, maturity, no overwrite, no double spend,
  version-3 rules, canonical witnesses and every input signature under its
  suite (0x0001, 0x0002, 0x0003);
- the coinbase pays at most the subsidy plus fees and the witness-share
  outputs exactly (DESIGN-witness-shares.md);
- applying `B` to `S(sp(B))` gives a set whose commitment is `SC(B)`.

Out of the relation, checked natively by every node as today because they
are cheap or DAG-wide: proof of work, `bits` and stall relief
(DESIGN-obenblock.md §4, §5.1), parents, GhostDAG coloring and blue work,
block size, and the PoWit section (votes, evidence, share validity).
OPEN: whether the PoWit section and the witness-share checks move into the
relation.

`SC(B)` is public in the proof and is checked against the commitment that
the next selected-chain block carries; a proof thus links two consecutive
commitments.

### Proof object (peer services, phase 1)

```text
proof_item = u8(version = 1) ‖ u32le(chain_id) ‖ u16le(system_id)
           ‖ rules_id[32] ‖ block_id[32] ‖ SC(sp(B))[32] ‖ SC(B)[32]
           ‖ varint(len) ‖ proof[len]
```

- Gossiped as a new PoWit-pool item kind (OPEN: kind number, per-peer
  budget, maximum `len`). A node relays a proof only after verifying it.
- `system_id` names the proof system and its parameters (OPEN: registry).
  Nodes accept only systems their release enables.
- Optional aggregation: a recursive proof over a run of consecutive blocks,
  e.g. the 60 blocks of one checkpoint interval, with public inputs the
  first `SC(sp(·))` and the last `SC(·)` (OPEN: whether phase 1 defines it).
- Proofs are not consensus objects in phase 1: a block is valid with or
  without a proof of it. OPEN: a later phase may commit proofs in blocks;
  that would be a separate OBIP.

### Use by voters and nodes (node-local policy)

- **Full nodes keep executing.** In phase 1 a node never accepts a block on
  a proof alone. A proof that verifies for a transition the node's own
  execution rejects is evidence of an unsound circuit or proof system: the
  node raises an alert (`getfinalityinfo` alert channel, as A2 conflicts)
  and stops trusting that `system_id`.
- **Proof-verifying voters** (opt-in mode of the witness duty): before
  voting for a link `(source, target)` (DESIGN-obenblock-poci.md §2,
  `msg_v3`), the duty either re-executes, or verifies a proof chain covering
  every selected-chain block from `source` to `target`. If proofs are
  missing, the duty falls back to execution; it never withholds its vote
  for lack of a proof. Finality liveness therefore never depends on a
  prover.
- **No new meaning for votes.** `msg_v3` is unchanged. A PoCI certificate
  says that more than two thirds of `C_e` signed the link; it does not say
  that they verified a proof, and a proof says nothing about which of two
  valid forks is final.

### Provers

- Anyone may prove; proofs are deterministic in their public inputs and the
  first valid one suffices.
- OPEN: incentives. The base pays nothing for proofs. Any payment out of
  the subsidy changes DESIGN-witness-shares.md and the tokenomics, and is
  not proposed here.
- OPEN: reference prover hardware, proving time per block (p50/p95/p99),
  and whether one prover can keep up with 30-second blocks.

| Quantity | Figure | Source |
| --- | --- | --- |
| Blocks per day | 2,880 | 30-second target (DESIGN-obenblock.md §4.2) |
| Proof bytes per day, one proof per block of 100 kB | about 288 MB | illustrative, not measured |
| Proof bytes per day, one recursive proof per checkpoint of 100 kB | about 4.8 MB (48 checkpoints) | illustrative |
| Signatures proven per input | one hybrid ML-DSA-65 + Falcon-1024 (about 4.6 kB) or SLH-DSA + Falcon | CONSENSUS.md "Witnesses" |

expected to dominate the prover's cost; the figure is OPEN.

## Rationale

- **Commit to the parent's state.** It avoids a self-referential coinbase
  and lets the miner fill the field from state it already has.
- **Soft fork for the commitment, peer service for the proof.** A
  commitment in the free coinbase bytes keeps old nodes on the chain; a
  proof outside the block keeps the block size and the miner's latency
  unchanged and lets proving lag behind production.
- **Separate from finality.** A valid proof of block A and a valid proof of
  a conflicting block B can both exist (the note's counterexample: one coin
  spent to Alice in A and to Bob in B). Only consensus picks one history.
  Making finality wait for proofs would also make PoCI liveness depend on
  provers, and requiring the proof of a target before its creation would
  create a cycle, because PoCI finalizes a source through a later target.
- **Execution kept in phase 1.** A circuit bug that accepts an invalid
  transition is an inflation bug if nodes trust it. Keeping execution
  turns such a bug into a detectable alert instead.
- **STARK, not a pairing SNARK.** ObenBlock's core is post-quantum
  (CONSENSUS.md "Conservative suite 0x0003"). Wrapping post-quantum
  signatures in a pairing SNARK and accepting only the SNARK makes the
  pairing assumption part of the ledger's security. The classical track is
  measured only as a baseline.
- **Fraud proofs (optimistic validity) instead.** Rejected for this OBIP:
  they need a challenge window, a data-availability guarantee for the
  challenger and a rule that reverts state, which conflicts with PoCI's
  sticky finality (DESIGN-obenblock-poci.md §11, O2).
- **Merged mining or a stake bond for provers.** Rejected for the base
  (DESIGN-obenblock.md §1: no merged mining, no stake) and not needed:
  a proof is checked, not trusted.
- **Anchoring the state commitment in Bloch.** An anchor proves only
  that its signer published it (BLOCH-ANCHOR.md "Who to trust",
  DESIGN-obenblock.md §8 advisory anchors); it adds no validity.

## Backwards Compatibility

- Activation at a coordinated ObenBlock release height (OBIP-1). Nodes that
  do not upgrade keep following the chain (the commitment uses bytes they
  already accept) but do not enforce it, so miners must upgrade before the
  height: a non-upgraded miner's block lacks the commitment and is invalid
  for upgraded nodes.
- No change to `msg_v3`, `config_id`, `params_digest` or certificates.
- Wallets see no change; `getblock` gains the commitment (OPEN: field name).
- GnB is unaffected; the chain ids keep the chains apart
  (DESIGN-obenblock.md §2).

## Security Considerations

- **Soundness assumptions.** A STARK's soundness rests on the hash function
  and the proof parameters (technical note R13); it is believed post-quantum
  under those assumptions. Groth16 and other pairing SNARKs, and BLS
  aggregation, are **not** post-quantum and also need a trusted setup for
  Groth16. No proof size or proving time for ObenBlock's relation has been
  demonstrated; the 1 KiB target of the technical note is not claimed.
- **Circuit correctness.** The circuit is a second implementation of the
  ledger rules. Every divergence is a consensus risk; it needs its own
  reference vectors against `reference/` and differential testing.
- **Data availability.** A proof does not make data available. A node that
  verifies proofs but lacks the block body cannot build transactions or
  reconstruct the state.
- **Validity is not uniqueness.** Two conflicting blocks can both have valid
  proofs. Wallets must keep crediting at PoCI finality (DESIGN-obenblock.md
  §7), not at "proven".
- **Denial of service.** Proof verification must be bounded by size and
  verified only for blocks that passed the native checks; invalid proofs
  cost the relaying peer its budget.
- **Prover concentration.** If few parties can afford proving, proof-only
  voters depend on them for convenience; the fallback to execution keeps
  that from becoming a liveness or safety dependency.
- **Post-quantum status of the whole path.** The commitment and accumulator
  are hash-based; the proof system on the mainnet path must be too. One
  hybrid ML-DSA-65 + Falcon-1024 signature is about 4.6 kB, so a block with
  many inputs has a large witness that the prover must process.

## Deployment prerequisites

- Choice and benchmark of `ACC` (update cost, memory, in-circuit cost).
- A prototype circuit for the relation, with measured proof size, proving
  time and verification time on stated reference hardware, for both the
  post-quantum track and the classical baseline.
- Differential tests of the circuit against the native ledger code and
  `reference/` models.
- A decision on prover incentives (or explicitly none).
