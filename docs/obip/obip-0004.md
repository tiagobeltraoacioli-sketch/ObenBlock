## Abstract

The base specification reads Bloch anchors through a Bloch RPC endpoint that
the operator trusts (`--bloch-rpc URL`, DESIGN-obenblock.md §8, phase 1). This
OBIP replaces that trust with a Bloch light client inside the ObenBlock node.
The node starts from a Bloch trust anchor shipped with the release. It follows
Bloch finality by checking Bloch's own finality votes against Bloch's
per-period light-client roster. It then checks anchor records with state
proofs against a Bloch state root it has verified. Bloch RPC endpoints become
untrusted data sources. Anchors stay advisory, as in the base. This OBIP
changes where the node gets the anchor from, not what the anchor is allowed
to do.

## Motivation

- DESIGN-obenblock.md §8 lists "a Bloch light client in the node (header sync
  of Bloch finality), removing the trusted Bloch RPC" as phase 2. The base
  implements phase 1 only.
- With phase 1, one compromised or wrong Bloch RPC endpoint can do two things:
  - show a false anchor, so the node raises a false conflict alert and the
    operator may act on it;
  - hide a real conflicting anchor, so the node shows false corroboration.
  The node cannot tell either case apart from honest behaviour.
- The note "Votos sobre shares, provas compactas e finalidade segura" (p. 17,
  [R16]) says it directly: an isolated RPC is not proof of Bloch finality.
  Use your own node or a light client whose initial trust is defined.
- Running a full Bloch node next to every ObenBlock node costs a lot. A Bloch
  node replay takes on the order of an hour on devnet4 (Bloch light-client
  proposal §5). A light client that follows one roster period at a time
  costs much less.
- The other direction (BLOCH-ANCHOR.md, BLA1 anchors recorded in ObenBlock)
  has a similar weak point. The anchoring program trusts that at least two
  Bloch RPC sources agree. The same light client can check that instead.

## Specification

### Terms

- **Bloch checkpoint**: Bloch's FFG `(epoch, block id)`, its block height and
  its post-state root. These are the fields BLOCH-ANCHOR.md reads from
  `getchaininfo.finalized`.
- **Roster leaf**: Bloch's per-period light-client roster. It is a state leaf
  (tag `0x23` on Bloch devnet4) that commits a Merkle root of
  `(index, weight, KES key commitment)` and the total weight. Bloch's
  consensus writes it one period ahead (Bloch light-client proposal §3, §5).
- **Step**: one move of the light client from a verified period to the next.
  This is the rule of Bloch's own "step" program, run natively.

### Trust anchor

- Each ObenBlock release ships `BLOCH_LC_ANCHOR = (epoch, block_id,
  state_root)`. This is a Bloch checkpoint finalized at or after the
  activation of the roster leaf on the Bloch network the release targets.
- OPEN: whether an operator may override the anchor
  (`--bloch-lc-anchor`), and how the node reports an overridden anchor.
- The anchor is weak subjectivity, in the same sense as the PoCI launch
  checkpoint (DESIGN-obenblock-poci.md §9). The node does not derive it from
  data alone.

### Step rule (native, post-quantum)

From a verified checkpoint with state root `S` in period `p`:

1. Get, from any untrusted source, the roster leaf for `p` (and for `p+1`
   when the step crosses a period boundary), with its sparse-Merkle inclusion
   proof against `S`. Check the proof.
2. Get a Bloch finality link `(E, id(H)) -> (E+1, R')` and the Bloch blocks
   that include its votes, ending at a header whose ancestry reaches `H`.
3. For each vote, check:
   - its signer's KES key commitment against the roster leaf, using the
     roster's weight and never a weight the vote states;
   - the KES path;
   - the hybrid ML-DSA-65 + Falcon-1024 signature.
   Use the verification code of Bloch's consensus crate
   (`bloch-pos-committee`), unchanged.
4. Accept `(E, id(H))` as final when the distinct verified signers hold at
   least 2/3 of the roster weight of `period_of(E+1)`. This is Bloch's
   threshold, which is inclusive. Then take `H`'s post-state root as the new
   `S`.
5. Advance at most one period per step, as in Bloch's step program.

A node that is behind runs steps until it reaches the newest Bloch checkpoint
any of its sources can prove.

### Anchor check

- With a verified Bloch state root `S`, the node reads the anchor registry
  entry for each ObenBlock slot it cares about, with an inclusion proof (or a
  non-inclusion proof) against `S`.
- The record is the base record (DESIGN-obenblock.md §8):
  `chain_id ‖ slot ‖ block_id ‖ finalized_at ‖ W-digest`.
- If OBIP-3 is active, the same state proof carries `record_v2`; whether
  the record is certified is then decided by OBIP-3, not by this OBIP.
- OPEN: the registry's storage layout and its proof format. These depend on
  the Bloch anchor registry, which does not exist yet.
- The result goes to the existing advisory path, unchanged:
  - an agreeing record is reported as corroboration;
  - a contradicting record, or one that names a block the node lacks, raises
    the A2 conflict alert (`getfinalityinfo`);
  - the operator decides with `setfinalitycheckpoint` / `ignorefinalized`.
  An anchor never sets a checkpoint by itself.

### Data sources

- `--bloch-rpc URL[,URL…]` stays, as a list of untrusted proof servers.
- The node needs these calls:
  - a block call (`getblockraw`);
  - a state-proof call (`getstateproof`: the leaf plus its siblings);
  - the roster call (`getlcroster`).
- OPEN: whether ObenBlock P2P relays Bloch proofs (a Peer Services
  extension), or the node only fetches them over RPC.
- When the sources disagree, the node keeps the proofs that verify. When two
  sources each prove a different Bloch checkpoint final for the same epoch,
  the node raises a Bloch-finality conflict alert and stops using anchors
  above the last checkpoint both proofs share. It does not pick one.

### RPC

- `getblochlcinfo`: anchor, verified checkpoint, period, last step time,
  sources and their state, and conflict state.
- OPEN: exact fields.

### Optional succinct mode

- Bloch's SP1 step and release programs end in a Groth16 wrapper (356-byte
  proof on devnet4). A node could accept such a proof in place of the votes.
- Groth16 is a pairing-based SNARK and is **not post-quantum**.
- So this mode, if it is supported at all, is off by default, labelled
  non-PQ in `getblochlcinfo`, and never used for the conflict alert without
  native verification.
- OPEN: whether to support it at all.

### Parameters

- OPEN: the period length on Bloch mainnet. The proposal is 256 epochs,
  about 68 h. It is a Bloch decision.
- OPEN: the maximum proof bytes and votes the node accepts per step.
- OPEN: the step polling interval.

## Rationale

- **Native votes rather than a SNARK.** Bloch's finality votes are already
  hybrid post-quantum signatures. Checking them natively keeps the
  post-quantum property. Bloch mainnet has about 43 votes per epoch
  (proposal §3, 64 genesis validators). One step per period stays small for
  a full node, even at roughly 4.6 kB per hybrid signature plus KES paths.
  The SNARK path exists for EVM contracts, where gas and calldata decide.
  That does not apply to an ObenBlock node.
- **Reuse Bloch's consensus code** rather than writing it again, so the
  light client cannot drift from Bloch. The Bloch light-client crate already
  follows this rule.
- **A roster per period rather than rebuilding the duty roster.** Bloch's
  per-epoch roster weights are not committed in state (proposal §3).
  Rebuilding them would need non-inclusion proofs and Bloch's leak rule.
  This is the sync-committee / validator-set-hash model.
- **Anchors stay advisory.** The base made them advisory because a record
  carries no proof that ObenBlock's configuration finalized it, and anyone can
  publish first. A verified Bloch state root fixes who published what on
  Bloch. It does not fix that. Automatic use needs a PoCI certificate checked
  by the registry or by the node (DESIGN-obenblock-poci.md §6). That is
  OBIP-3, out of scope here.
- **Self-anchoring rejected.** The base rejects self-anchoring: ObenBlock
  cannot vouch for its own finality through its own data. The light client
  does not change that. It verifies a second chain's finality, it does not
  restate ObenBlock's.
- **Running a full Bloch node** stays allowed (a trusted `--bloch-rpc` on
  localhost). It is not the default, because of its cost.

## Backwards Compatibility

- No consensus change. A node that does not run the light client keeps the
  phase-1 behaviour.
- Activation is a coordinated ObenBlock release that ships the anchor. No
  height is needed for the node-local part.
- GnB is unaffected.

## Security Considerations

- **Assumptions.**
  - Less than 1/3 of Bloch's roster weight per period is Byzantine.
  - The release anchor is honest.
  - Bloch's KES erasure works. The Bloch proposal relies on it against
    long-range rewrites, which is a Bloch design claim that this OBIP does
    not re-prove.
  - Bloch's consensus code is correct.
- **Bloch's own leak.** Bloch's roster weights include its inactivity leak
  (proposal §3). The partition analysis of DESIGN-obenblock-poci.md §1
  applies to any finality with a leak. The light client must therefore expect
  two conflicting Bloch finalized checkpoints after a long Bloch partition. It
  reports this as a conflict and does not pick one.
- **Eclipse.** If every source withholds new steps, the node falls behind.
  It does not accept anything false. `getblochlcinfo` reports how long ago
  the last step was.
- **Denial of service.**
  - Native checking costs one hybrid signature check per vote.
  - Limits on proof bytes and votes per step are OPEN.
  - The node checks a roster inclusion proof before it checks any signature.
- **Post-quantum status.**
  - The native mode keeps Bloch's ML-DSA-65 + Falcon-1024 hybrid. One
    signature is about 4.6 kB.
  - The SP1/Groth16 mode is not post-quantum.
  - A STARK proof without the Groth16 wrapper would be post-quantum under
    hash assumptions. It would be tens to hundreds of kB, and it has not been
    measured for this relation.
- **What does not change.** The light client removes trust in an RPC
  endpoint. It does not make anchors authoritative. It does not protect
  clients that settled on another history before an anchor existed.

## Deployment prerequisites

- The roster leaf active on Bloch mainnet. As of 2026-10-18 it is only on
  devnet4, from epoch 12288.
- `getstateproof` and `getlcroster` served by Bloch nodes.
- The Bloch anchor registry and its proof format. DESIGN-obenblock.md §8 says
  this needs the Bloch repository.
- A Bloch block and vote wire format frozen for the target network.
- The dependency decision on Bloch's consensus crate inside ObenBlock.
