# OBIP-7: Bloch-authorized finality recovery

```

  Layer: Consensus (hard fork)
  Title: Bloch-authorized finality recovery
  Author: gnb-smh <gnb-smh@proton.me>
  Status: Draft
  Type: Standards Track
  Created: 2026-10-18
  License: BSD-2-Clause
  Requires: 4
```

## Abstract

Under PoCI (base specification DESIGN-obenblock-poci.md) finality halts when
more than a third of the configuration in force, `C_e`, stops voting at once.
If that weight never returns, the base specification (§7) offers only a
manual recovery: a release names a recovery checkpoint and a new
configuration, and operators apply it with `setfinalitycheckpoint`. This OBIP
proposes a second, protocol-defined path. After a stall of at least
`RECOVERY_STALL_EPOCHS` epochs, one record finalized on Bloch authorizes a
recovery round. Every node then computes the same recovery configuration
from data it already shares: the last finalized checkpoint `F`, the round
number `r`, and the selected chain of a recovery base block `B` named by the
record. The recovery configuration votes under its own `config_id`. It
finalizes `B` (or a later checkpoint) only with a strict quorum of its own
weight. The manual procedure of §7 stays as the fallback. This OBIP makes
ObenBlock depend on Bloch for this one decision, and it says so plainly: the
recovery inherits Bloch's safety and liveness assumptions.

## Motivation

- DESIGN-obenblock-poci.md §4.1 removes weight that fades out, through
  handoffs that `C_e` itself finalizes. It states the limit: when more than a
  third of `C_e` vanishes at once, "`C_e` has no quorum to authorize
  anything", and "no rule inside one partition can safely decide that the old
  committee is gone".
- The base partition simulator (branch `obenblock/o11b-partition-sim`,
  `docs/research/obenblock-partition-sim.md`) confirms the halt. A 50/50
  partition or 40 % of the weight going offline at once halts PoCI finality
  until the weight returns. That is the intended safe behaviour. A permanent
  loss (keys destroyed, a large pool shut down) leaves the chain with
  provisional ordering only. Wallets and exchanges credit at finality
  (DESIGN-obenblock.md §7), so settlement stops.
- The manual path of §7 works, but it is slow and social. Every operator
  must install a release and run `setfinalitycheckpoint`. Operators who are
  late, or who never upgrade, stay on the halted configuration. Nothing in
  the protocol makes the recovering nodes agree on one recovery checkpoint
  and one configuration.
- The technical note "Votes on shares, compact proofs and safe
  finality" (p. 7 and p. 17) names the option this OBIP specifies: "Bloch can
  authorize a new configuration only if this function and its limits are
  defined in advance. It is an explicit trust dependency, not autonomous
  BFT." DESIGN-obenblock.md §8 already uses Bloch for mutual anchoring, so a
  record format and a registry exist on paper.

## Specification

All integers are little-endian unless stated. `SHA-256d` and the tagged
Merkle tree are those of DESIGN-obenblock-poci.md §2. "Finalized history"
has the base meaning.

### Terms

- `F`: the node's last finalized checkpoint, `(height, hash)`, finalized
  under `C_e`, the configuration in force.
- **Stall**: no checkpoint above `F` is finalized.
- `B`: the **recovery base**. It is a checkpoint slot that opens an epoch,
  and it lies on a selected chain that descends from `F`.
- **Round** `r`: a counter that starts at 0 for each `F`.
- `C^R(F, r)`: the recovery configuration of round `r`.

### Parameters

| Name | Meaning | Value |
|---|---|---|
| `RECOVERY_STALL_EPOCHS` | minimum `epoch(B) - epoch(F)` before round 0 | OPEN: must exceed any partition the network should survive without outside help; at least the base window (112 epochs) is one candidate, one or two `PRUNE_AFTER` periods another |
| `RECOVERY_ROUND_EPOCHS` | minimum distance, in epochs of chain height, between the bases of rounds `r` and `r+1` | OPEN |
| `RECOVERY_MAX_ROUNDS` | rounds allowed per `F` before only the manual path remains | OPEN |
| submitter policy | who may publish a record on Bloch | OPEN (see below) |
| Bloch confirmation | what counts as "finalized on Bloch" for the node | Bloch FFG finality as verified by OBIP-4 |

### Recovery seed

```text
recovery_seed(F, r) = SHA-256d( "OBB-OBIP7/seed" ‖ u32le(chain_id)
                                ‖ u64le(F.height) ‖ F.hash[32] ‖ u32le(r) )
```

The seed is a pure function of `F` and `r`. It does not depend on any
choice made after the stall began. It is used only for domain separation
(below). It does not select voters, samples or a committee.

### Recovery configuration

`C^R(F, r)` is computed exactly like a handoff of DESIGN-obenblock-poci.md
§4 to the epoch `x = epoch(B)`, with history read from the selected chain of
`B` up to `B`, as if `B` had been finalized under `C_e`:

- entries and weights from share work in the window that ends before `x`,
  with the growth cap of DESIGN-obenblock.md §6.3, applied epoch by epoch
  from the last configuration in force;
- exits, bans and the absence pruning of DESIGN-obenblock-poci.md §4.1 as
  that handoff would apply them;
- `params_digest` unchanged.

Its identifier uses its own tag and commits the seed, so that a recovery
configuration never shares an id with an ordinary configuration, or with
another round:

```text
recovery_config_id = SHA-256d( "OBB-OBIP7/config" ‖ u32le(chain_id) ‖ u64le(x)
                               ‖ u128le(total) ‖ merkle_root(entries)
                               ‖ params_digest ‖ recovery_seed(F, r) )
```

Votes of round `r` use the attestation message v3 of the base specification
with `config_id = recovery_config_id`. A vote counts only for the
configuration it names, as in the base.

### Bloch record (version 1)

The record is a Bloch transaction to the anchor registry of
DESIGN-obenblock.md §8. Its payload:

```text
u8(version = 1) ‖ u8(kind = 0x07)              // recovery authorization
‖ u32le(chain_id)
‖ u64le(F.height) ‖ F.hash[32]
‖ config_id(C_e)[32]                            // the halted configuration
‖ u32le(r)
‖ u64le(B.height) ‖ B.hash[32]
‖ recovery_config_id[32]
‖ submitter authorization                       // OPEN, see below
```

OPEN: how this record kind is told apart from base anchor records and from
OBIP-3 `record_v2` (a shared registry envelope).

Bloch-side registry rules (OPEN until the Bloch code base is available,
DESIGN-obenblock.md §10 open point 1):

- at most one finalized record per `(chain_id, F, r)`;
- a record for round `r + 1` is accepted only after the record of round `r`
  for the same `F` is finalized on Bloch;
- if the registry holds an anchor (DESIGN-obenblock.md §8) for `chain_id`
  above `F.height`, the record is rejected. This check helps but does not
  prove that `F` is the last finalized checkpoint, because base anchors are
  advisory.

### Node rules

A node applies a record only when all of the following hold. Otherwise it
ignores the record and reports it in `getfinalityinfo`.

1. The record is finalized on Bloch, as verified by the Bloch light client of
   OBIP-4. A trusted Bloch RPC is not enough for this rule.
2. `chain_id` is the node's own, and `F` equals the node's last finalized
   checkpoint. `config_id(C_e)` is the configuration in force.
3. `B` is a known, valid block. It is a checkpoint slot that opens an epoch,
   `B` descends from `F`, and `epoch(B) - epoch(F) >= RECOVERY_STALL_EPOCHS`.
4. For `r > 0`: the node applied round `r - 1` for the same `F`, it holds no
   certificate under `C^R(F, r - 1)`, and `epoch(B_r) - epoch(B_{r-1}) >=
   RECOVERY_ROUND_EPOCHS`.
5. The node recomputes `C^R(F, r)` from `B`'s chain and gets
   `recovery_config_id`. A mismatch is an error. The node does not apply the
   record and raises the conflict alert of package A2.
6. `r < RECOVERY_MAX_ROUNDS`.

When it applies a record, the node:

- treats `B` as the **justified source** for votes under `C^R(F, r)`. `B` is
  not final. It becomes final only by the ordinary FFG rule: a strict quorum
  of `C^R(F, r)` on the link `B → B + checkpoint_interval`. The quorum rule
  of DESIGN-obenblock-poci.md §3 applies unchanged to `C^R`;
- stops counting votes under `C_e` for links above `F`. A certificate under
  `C_e` above `F` that arrives later and conflicts with a checkpoint
  finalized under `C^R` raises the A2 conflict alert. It is never resolved
  automatically;
- after `C^R(F, r)` finalizes a checkpoint, continues with the ordinary
  handoffs of §4 from that configuration. Recovery leaves no lasting state.

The witness duty votes under `C^R(F, r)` only when its key is an entry of it.
Signer protection (DESIGN-obenblock-poci.md §8) keys its record by
`config_id`, so votes under `C_e` and under `C^R` never collide in the
record.

### Submitter policy (OPEN)

Whoever publishes the record chooses `B`, and so chooses the history the
recovery configuration is read from. This draft does not pick a policy. The
candidates are:

- (a) any Bloch account, first record wins (the base anchor rule). This is
  not acceptable alone. The base already treats "first record wins" as
  unfit for automatic use (DESIGN-obenblock.md §8), and a submitter could
  pick a branch where its own share work is heavier.
- (b) an m-of-n set of recovery keys named in the activation release, with
  hybrid PQ signatures. The trust is explicit, and the same people could run
  the manual path faster.
- (c) (b) plus a challenge period on Bloch. A competing record for the same
  `(F, r)` with a heavier-work `B`, by a rule Bloch can check, replaces the
  first one. OPEN whether Bloch can check ObenBlock work without an ObenBlock
  light client.
- (d) a canonical `B` that needs no choice, for example the epoch-opening
  checkpoint at a fixed height above `F` on the chain with the most work.
  OPEN: nodes do not agree on a selected chain above `F` during a stall,
  which is why the record names `B`.

## Rationale

- **Why outside authority at all.** §4.1 shows that no rule inside one
  partition can tell "the other third is gone" from "the other third is
  behind a partition". Either a party outside the halted configuration
  decides, or nobody does. The base keeps "nobody" (manual). This OBIP adds
  Bloch as that party, under rules fixed in advance.
- **Why Bloch, and why one finalized record.** Bloch has BFT finality of its
  own, and it is already the anchor chain (DESIGN-obenblock.md §8). One
  finalized record gives every ObenBlock node the same `(F, r, B)` without a
  vote among ObenBlock operators who have no quorum.
- **Why the record names `B` and the nodes compute the configuration.**
  The record cannot carry a configuration that nobody can check. Making it
  a deterministic handoff from data every node holds limits the record to
  one choice (`B`) and one check value (`recovery_config_id`). The growth cap
  (§6.3) still bounds how much new weight `B`'s chain can contain.
- **Why `B` is only justified, not final.** If Bloch finalized ObenBlock
  blocks directly, ObenBlock finality would be Bloch's. Requiring a strict
  quorum of `C^R` keeps ObenBlock votes as the source of finality, and
  equivocation under `C^R` stays provable (§5).
- **Why a seed of `(F, r)` only.** The seed cannot be ground, because it
  depends on nothing chosen after the stall. A seed derived from proof bytes
  or signature lists would allow retries (note p. 14).
- **Rejected: random multi-round recomposition.** Sampling a new committee
  from the seed at each failed round trades the guarantee over all weight
  for a sample, and each new draw is another chance for an attacker (note
  p. 8: with `k = 100` seats and an adversary at 25 %, a draw exceeds a third
  with probability about 2.76 %). The base already rejected it. Rounds here
  change the base block and nothing else.
- **Rejected: local committee change on timeout.** This is the faster leak
  of DESIGN-obenblock.md §5.2. PoCI exists to remove it, and the simulator
  shows it finalizes both sides of every long partition.
- **Rejected: self-anchoring.** ObenBlock cannot authorize its own recovery
  from inside the halted configuration, for the reason in the first point.
- **Rejected: stake bond on Bloch as the authority.** ObenBlock weight is
  share work only (DESIGN-obenblock.md §1). A bond would add an economic
  layer that the base rejected. A bond for submitters under policy (c) is
  OPEN, and it would be a Bloch-side matter.
- **Rejected: merged mining with Bloch or another chain.** This does not
  recover a configuration, and the base rejected merged mining (§1).
- **Alternative kept: manual recovery (base §7).** It remains for every case
  this OBIP does not cover: Bloch down, round limit reached, a record
  mismatch, or a conflict alert.

## Backwards Compatibility

This is a hard fork of ObenBlock. Nodes that do not implement it ignore
recovery records and stay on the halted configuration. Activation is a
coordinated ObenBlock release height. Before that height no record has any
effect. GnB is unaffected: GnB does not use PoCI and does not read the
registry.

## Security Considerations

- **Bloch dependency, stated plainly.** For recovery, ObenBlock's safety and
  liveness become Bloch's. If Bloch finality is faulty (more than a third of
  Bloch stake Byzantine, a Bloch bug), Bloch can authorize a wrong round. If
  Bloch finality stalls, recovery waits and the manual path remains. If the
  Bloch validators censor the registry, recovery does not happen. ObenBlock
  operators who also run Bloch validators do not create independence (note
  p. 18).
- **Hidden partition.** If `C_e` still holds more than two thirds behind a
  partition that the submitter cannot see, `C_e` may finalize a checkpoint
  above `F` while `C^R` finalizes a conflicting one. Votes under different
  `config_id`s are not evidence under §5, so this conflict is **not
  accountable**. It is the price of any recovery from outside the
  configuration. `RECOVERY_STALL_EPOCHS` is the only defence, and it is not
  a proof. Nodes keep both certificates and raise the A2 alert.
- **Cross-configuration evidence.** A key that is an entry of both `C_e` and
  `C^R` could sign conflicting links under each. Whether such a pair should
  be evidence is OPEN. Defining it needs a rule that relates checkpoints
  across two configurations.
- **Choice of `B`.** See the submitter policy. Under every policy the growth
  cap bounds the new weight per epoch on `B`'s chain. It does not bound the
  result. The cap's capture bound (about 71 epochs from honest-only weight
  to two thirds, DESIGN-obenblock.md §6.3) is shorter than a stall longer
  than 71 epochs. Also, the honest miners who left lose their weight as it
  expires from the window. Then the share work on `B`'s chain may be mostly
  an attacker's, the recovery configuration belongs to the attacker, and no
  rule here can tell.
- **Rounds.** Each round is a fresh configuration with no accountable link
  to the previous one. `RECOVERY_MAX_ROUNDS` bounds the number of such
  chances.
- **Post-quantum status.** The record is a Bloch transaction, so its
  signatures are Bloch's. The Bloch light client of OBIP-4 verifies Bloch
  finality natively. A succinct proof of Bloch finality based on pairing
  SNARKs (Groth16, BLS aggregation) is **not** post-quantum. A STARK proof is
  tens to hundreds of kB. Votes under `C^R` carry the base hybrid signatures
  (ML-DSA-65 + Falcon-1024, about 4.6 kB each).
- Recovery does not undo payments settled on another history (base §7).

## Deployment prerequisites

- OBIP-4 (Bloch light client in the node), deployed and verifying Bloch
  finality.
- The Bloch anchor registry with the record kind above. This needs access to
  the Bloch code base (DESIGN-obenblock.md §10 open point 1).
- A decision on the submitter policy and on `RECOVERY_STALL_EPOCHS`,
  `RECOVERY_ROUND_EPOCHS` and `RECOVERY_MAX_ROUNDS`.
- A reference model in `reference/` with vectors, and the base partition
  simulator extended with recovery rounds, including the hidden-partition
  case.
- The documented manual procedure of base §7, kept and tested as the
  fallback.
