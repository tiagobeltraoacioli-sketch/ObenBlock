## Abstract

This Informational OBIP describes how ObenBlock could serve as a settlement
layer for execution layers (L2) that run off L1, while keeping the L1 small
enough for independent nodes to verify. An L2 posts to L1 its transaction
data (or a commitment with stated availability), a new state root and a
validity proof of the transition; L1 verifies the proof and settles only at
PoCI finality (DESIGN-obenblock-poci.md §6). Users must be able to **exit
without the sequencer's goodwill**: a forced-inclusion queue on L1 and an
escape hatch that lets anyone withdraw against the last settled state if the
sequencer stops. None of this exists in the base: ObenBlock's spend policies
(`obb1m…`, DESIGN-obenblock.md §2) cannot express "spendable only with a
valid proof", so a trust-minimized L2 needs new L1 consensus rules and a
post-quantum proof system (OBIP-10). The document lists the components, the
L1 capacity they consume, the assumptions each design adds, and what is
still open. It proposes no rule for activation.

## Motivation

- The technical note behind PoCI (p. 18, P2) recommends keeping the L1
  within limits that independent nodes can verify and moving bulk execution
  into proven batches or an L2, with the condition that users can verify
  settlement, recover data and leave without depending on a sequencer.
- L1 capacity is bounded: 1,000,000 bytes per block (CONSENSUS.md "Block
  size (VAL-12)") every 30 seconds, about 33 kB/s. One hybrid ML-DSA-65 +
  Falcon-1024 signature is about 4.6 kB (CONSENSUS.md "Witnesses"), so
  post-quantum transactions are large and L1 throughput is low.
- A federation (an m-of-n spend policy) can already hold L2 funds today, but
  then exits depend on the signers; that is a custodial bridge, not a
  settlement layer.

## Specification

Informational: components and requirements, not rules.

### Roles

- **Sequencer**: orders L2 transactions and builds batches. OPEN: single,
  rotating, or permissionless.
- **Prover**: produces the validity proof of a batch. Anyone may prove.
- **L1 bridge output**: an L1 output that holds the L2's deposited OBB and
  whose spend rule is the L2's settlement rule.

### L1 components needed

1. **Proof verification in L1 consensus.** A new output kind or spend
   policy (OPEN: encoding) whose spend requires a batch object:

   ```text
   batch = ( l2_id[32], prev_state_root[32], new_state_root[32],
             data_commitment[32], forced_queue_head[32], withdrawals_root[32],
             system_id, proof )
   ```

   valid iff `prev_state_root` equals the bridge output's current root, the
   proof verifies the transition under the L2's registered program, the
   batch consumed the forced queue up to `forced_queue_head` (below), and the
   new bridge output carries `new_state_root`. OPEN: whether this is a new
   transaction type, an extension of spend policies (CONSENSUS.md "Spend-
   policy key identity (PF-4)"), or a covenant primitive.
2. **Proof system.** The same family as OBIP-10 (hash-based, STARK family,
   for the post-quantum path). OPEN: verification cost per block, which must
   enter CONSENSUS.md "Per-block cost" limits; proofs are tens to hundreds
   of kB, a significant share of a 1 MB block.
3. **Data availability.**
   - *On L1* (rollup): the batch's data (state differences or
     transactions) is in the L1 block. Exits then rely only on L1.
   - *Off L1* (validium or external DA): only `data_commitment` is on L1.
     If the data is withheld, users can prove nothing about their balance
     and cannot exit; this design does not meet the exit requirement unless
     a DA guarantee is stated and verified. Sampling bounds from the
     technical note (P1: e.g. 32 samples miss a 10 % gap with 3.4 %
     probability) apply only with honest, unpredictable sampling and
     correct erasure coding.
4. **Forced inclusion.** A user posts an L1 transaction into the bridge's
   forced queue (deposit, L2 transfer or withdrawal request). A batch is
   valid only if it consumes every queue entry older than `D_force` L1
   blocks (OPEN: `D_force`), so a sequencer can delay a user by at most
   `D_force` blocks but cannot censor.
5. **Escape hatch.** If no batch settles for `D_escape` finalized L1 blocks
   (OPEN), the bridge enters exit mode: anyone may prove an account or coin
   against the last settled `new_state_root` (an inclusion proof under the
   L2's state tree) and withdraw it, once. OPEN: the nullifier or bitmap that
   prevents double exits, and whether exit mode is permanent.
6. **Settlement at finality.** The bridge rule takes effect for withdrawals
   only once the block holding the batch is PoCI-final (DESIGN-obenblock.md
   §7). Timeouts `D_force` and `D_escape` count finalized L1 blocks, not
   wall-clock time, so a PoCI halt (DESIGN-obenblock-poci.md §7) pauses both
   instead of triggering exit mode on one side of a partition.

### What the user must be able to do alone

| Need | Mechanism | Depends on |
| --- | --- | --- |
| Verify a batch | check the proof (or trust an L1 node that did) | proof soundness, L1 finality |
| Recover the L2 state | read the batch data from L1 | data on L1 (rollup case) |
| Force a transaction | L1 forced queue | L1 inclusion, `D_force` |
| Leave if the sequencer stops | escape hatch | last settled root, `D_escape`, L1 liveness |

### Capacity (illustrative, to be measured)

| Item | Figure |
| --- | --- |
| L1 bytes per second | about 33 kB/s (1,000,000 bytes per 30 s) |
| One batch proof | OPEN; STARK proofs are tens to hundreds of kB |
| Batch data per transfer | OPEN; a validity rollup need not post signatures (the proof covers them), only state differences |
| A forced transaction on L1 | at least one hybrid signature, about 4.6 kB, plus the request |

The gain depends on bytes of state difference per L2 transaction against the
roughly 4.6 kB of signature an L1 transaction carries; no figure is claimed.

## Rationale

- **Validity proofs, not fraud proofs.** Optimistic rollups need a challenge
  period, a challenger with the data and an L1 that can re-execute the
  disputed step. They also revert state, which conflicts with sticky
  finality (DESIGN-obenblock-poci.md §11). Validity proofs settle at once
  after finality.
- **Federated bridge** (m-of-n policy): available today but exits depend on
  the signers' goodwill; it fails the requirement and is not a settlement
  layer.
- **Merged mining** to secure an L2 with the L1's hashrate: rejected for the
  base (DESIGN-obenblock.md §1) and does not give exits.
- **Stake bond for sequencers**: rejected for the base (no stake); forced
  inclusion and the escape hatch remove the need to trust the sequencer
  instead of insuring against it.
- **Self-anchoring or anchoring in Bloch** as settlement: an anchor proves
  only its signer's view (BLOCH-ANCHOR.md "Who to trust",
  DESIGN-obenblock.md §8); it cannot release funds.
- **Execution on L1 instead** (larger blocks): raises the cost of an
  independent node, which the note's recommendation tries to keep low.

## Security Considerations

- **Proof soundness** is part of the bridge's custody: an unsound proof
  system or circuit can drain the bridge output. OBIP-10's differential
  testing applies; there is no native re-execution fallback for an L2
  program unless L1 runs it.
- **Post-quantum status.** Pairing SNARKs (Groth16) and BLS are not
  post-quantum; a bridge verified by them is not post-quantum even if L2
  signatures are. STARK proofs are hash-based and believed post-quantum, at
  tens to hundreds of kB.
- **Data withholding** defeats exits in any off-L1 DA design.
- **L1 liveness.** Exits need L1 inclusion and finality. During a PoCI halt,
  no withdrawal settles; the escape timers pause by construction.
- **Upgrade keys.** An L2 whose program can be upgraded by a key has that
  key as custodian. OPEN: whether the bridge rule allows upgrades only with
  a delay longer than `D_force + D_escape`, so users can leave first.
- **Concentration.** Sequencers and provers may concentrate; the forced
  queue and escape hatch bound what they can do, not who they are
  (OBIP-11 measures concentration only for L1 weight).

## Deployment prerequisites

- OBIP-10's proof system measured and chosen, with an L1 verification cost
  bound.
- A design of the L1 bridge primitive (output kind or covenant) with its
  own Standards Track OBIP, reference model and vectors.
- Decisions on `D_force`, `D_escape`, the DA model and upgrade rules.
