## Abstract

The base partition simulator found two weak points in how PoCI computes a
new configuration after a long stall or a long partition. First, after a
stall longer than the window, the first configuration holds only the few
keys that kept mining. Second, after a partition longer than the window, the
keys of the losing side leave the configuration and must come back as new
weight under the growth cap. Both cases are safe, but they leave a thin or
lopsided configuration. This OBIP proposes two deterministic rules, both
computed from finalized history only. (1) A **carry-over floor**: when a
handoff would cut the total weight below a fraction of the configuration in
force, part of the old configuration's weight is carried into the new one,
pro rata. (2) **Fast re-entry**: keys that held weight in a recent
configuration get priority inside the growth budget, up to their previous
weight. The total admitted per epoch never exceeds the growth cap. The OBIP
analyses the trade-off between safety and liveness that the carried weight
creates, and leaves the floor parameters open.

## Motivation

Base specification: DESIGN-obenblock-poci.md §4 (handoff), §4.1 (absence
pruning by the old committee), DESIGN-obenblock.md §6.2 (112-epoch window)
and §6.3 (growth cap). The simulator is on branch
`obenblock/o11b-partition-sim` (`reference/sim/partition_sim.py`,
`docs/research/obenblock-partition-sim.md`). It does not model §4.1, which
came later.

1. **Thin configuration after a long stall.** Scenario
   `stall-exit-ban-expiry` (window shortened to 6 epochs): 40 % of the keys
   go offline from epoch 3 to 15. `C_2` (10 keys, total 590) stays in force,
   as PoCI requires. When the keys return, `C_2` finalizes and hands off to
   `C_15`, which holds **3 keys with total 180**. The returning keys reach
   `C_16` only through new share work and the growth cap. While `C_15` is in
   force, the 3 keys are the whole finality quorum. If they go offline, the
   chain stalls again. If one operator controls them, it controls finality
   alone.
2. **The losing side leaves the configuration.** Scenario `p50-window`
   (50/50 for the window plus 8 epochs): after the heal, `C_1` (11,200)
   hands off to `C_122`, computed from the winning branch only: **side A's
   5 keys, 5,600**. Side B's share work is on the orphaned branch. The
   simulator's note states that the winner of a tie (most work, then an
   arbitrary order) decides who keeps weight. With §4.1, a side that holds
   more than two thirds (70/30) prunes the other side's keys after
   `PRUNE_AFTER = 4` epochs, long before the window expires them. Those keys
   then need a rejoin message and the growth budget. Return of 30 % at the
   cap takes about `ln(1/0.7) / ln(65/64) ≈ 23` epochs (about 6 days), and
   only if no newcomer competes for the budget.
3. The simulator report asks for exactly this decision: "a floor on the
   entries of a configuration, or keeping the old configuration's keys for
   the first handoff".

## Specification

### Terms

At a handoff from `C_e` (in force; it finalized the triggering checkpoint)
to epoch `x`:

- `C_x`: the configuration the base rules compute (§4, §4.1, §6.3), with
  weights `w_x(k)` and total `T_x`;
- `w_e(k)`, `T_e`: weights and total of `C_e`;
- `E`: the entries of `C_e` that are not banned at `x` and have no
  finalized exit. Keys that §4.1 prunes at this handoff are in `E` only if
  their last included vote is less than `PRUNE_AFTER` epochs before
  `epoch(F)`, where `F` is the last checkpoint finalized before this one. In
  words: absence during a stall does not count as fading out. OPEN whether
  this reading of §4.1 holds across a handoff that skips epochs; see open
  questions.

### Parameters

| Name | Meaning | Value |
|---|---|---|
| `FLOOR_NUM / FLOOR_DEN` | weight floor, as a fraction of `T_e` | OPEN |
| `MIN_ENTRIES` | entry-count floor | OPEN |
| carry mode | `L` (liveness-preserving cap) or `S` (no cap) | OPEN; analysis below |
| `REENTRY_LOOKBACK` | epochs of past configurations that qualify a key for re-entry | OPEN; at most the window (112) |

### Rule 1: carry-over floor

```text
thin      = (T_x × FLOOR_DEN < T_e × FLOOR_NUM) or (|C_x| < MIN_ENTRIES)
target    = ceil(T_e × FLOOR_NUM / FLOOR_DEN)
D_raw     = 0                                      if not thin
          = max(target - T_x, cap_L)               if |C_x| < MIN_ENTRIES
          = target - T_x                           otherwise
cap_L     = floor((T_x - 1) / 2)                   (0 when T_x = 0)
D         = min(D_raw, cap_L)                      carry mode L
          = D_raw                                  carry mode S
c_k       = floor(w_e(k) × D / sum_{j in E} w_e(j))   for k in E (0 if E is empty)
w'_x(k)   = w_x(k) + c_k
C'_x      = entries with w'_x(k) > 0, strictly ascending by key_id
```

- All arithmetic is u128 with floors, as in §6.3. The products need a wide
  intermediate (u256) or an equivalent exact division. OPEN: the exact
  integer recipe for the reference model.
- `C'_x` replaces `C_x`. Its `config_id`, Merkle root and certificate rules
  are those of the base, unchanged. The carried weight is not marked in the
  registry.
- Carried weight is not share work. It does not enter `R_k` (the work
  leaving the window) at later handoffs. At the next handoff the floor is
  evaluated again against `C'_x`. So a floor ratio below 1 decays
  geometrically over successive thin handoffs, and stops as soon as share
  work refills the configuration.
- `cap_L` keeps the carried weight strictly below a third of `T_x + D`.
  Then `T_x / (T_x + D) > 2/3`, so the keys that kept mining can still reach
  a strict quorum alone (stall example: `T_x = 180`, `cap_L = 89`,
  `180 / 269 = 66.9 %`).

### Rule 2: fast re-entry inside the growth budget

```text
P_x       = keys that were entries of a configuration in force during the
            REENTRY_LOOKBACK epochs before x, not banned at x, and with a
            finalized rejoin message if §4.1 pruned them
prior_k   = the largest weight of k in those configurations
cur_k     = k's weight before this epoch's admission
claim_k   = min(x_k, max(0, prior_k - cur_k))      for k in P_x, else 0
            (x_k = new work above renewal, DESIGN-obenblock.md §6.3)
if sum(claim) <= G_e:
    admit_k = claim_k + share of the remaining budget G_e - sum(claim),
              pro rata over (x_k - claim_k) by the §6.3 rule
else:
    admit_k = floor(claim_k × G_e / sum(claim)), and nothing else is admitted
```

- `sum(admit) <= G_e` always. Rule 2 changes **who** gets the growth budget
  first, not **how much** is admitted per epoch.
- Renewal (`renew_k`) is applied first, as in §6.3, and is unchanged.

Rule 1 applies at the handoff. Rule 2 applies at each epoch step of the
window computation. A configuration computed by OBIP-7 (recovery) is a
handoff and applies both rules.

## Rationale

- **The trade-off cannot be avoided.** After `C_e` loses weight at once, a
  rule cannot both (a) let the keys that kept mining finalize alone when the
  others are gone for good, and (b) stop those keys from finalizing alone
  when they are an attacker. Carry mode `L` chooses (a). Carry mode `S` with
  a high floor chooses (b): the chain may halt again, and the remedy is the
  manual path (base §7) or OBIP-7. This OBIP specifies both modes so that
  the owner decides with the numbers.
- **Why a mixture and not "max of old and new weight".** With
  `w' = w_x + c` (a mixture of two weight functions) the share of any
  coalition `S` in `C'_x` is at most the larger of its share in `C_x` and
  its share of `E` by `C_e` weight (mediant inequality; floors only lower
  `c`). A per-key `max(w_x, λ w_e)` does not have this bound. With an honest
  key present in both configurations and a coalition split into one key
  that kept mining and one that left, the coalition holds 1/2 of each
  configuration but 2/3 of the `max` merge.
- **Why pro rata over `E`.** It keeps the composition of the configuration
  that last had a quorum. That configuration's weight was authorized by a
  finalized handoff. The carry needs no new choice and no randomness.
- **Why re-entry stays inside the cap.** Re-entry outside `G_e` (treating
  returning work as renewal) would restore the losing side in one handoff.
  It would also let any key of a past configuration return with up to
  `prior_k` at once, so the bound of §6.3 would become "the sum of past
  weights", not `W_e / 64` per epoch. Inside the cap, the 71-epoch capture
  bound of §6.3 is unchanged. That bound already assumes the attacker takes
  the whole budget.
- **Rejected: count orphaned-branch share work.** Shares on the losing
  branch attest blocks that are not on the finalized chain. Admitting them
  would let a private fork mint weight, the attack that the H2 rule
  ("witness set from finalized history", CONSENSUS.md PoWit) removed.
- **Rejected: local committee change.** Keeping the old keys by a local
  timeout reintroduces the leak of DESIGN-obenblock.md §5.2.
- **Rejected: random multi-round recomposition** to fill a thin
  configuration from a seed. The base rejected sampled committees (note
  p. 8).
- **Rejected: stake bond** as an alternative floor. Weight is share work
  only (DESIGN-obenblock.md §1).
- **Alternative: freeze `C_e` until the new configuration is "full".**
  Delaying the handoff keeps expired and exited weight in force. That
  breaks the base rule that exits, bans and expiry take effect at the next
  handoff.

## Backwards Compatibility

This is a hard fork of ObenBlock: it changes the configuration that counts
for finality. Activation is a coordinated ObenBlock release height. A
handoff at or above that height uses the new rules. Configurations already
in force and past certificates are unchanged and keep verifying under their
`config_id`. GnB is unaffected.

## Security Considerations

- **Accountable safety is unchanged.** Each decision still counts against
  one frozen configuration (base §2–§3). `C'_x` is a deterministic function
  of `C_e` and finalized history, and it enters into force through a
  handoff that more than two thirds of `C_e` finalized. Every honest node
  computes the same `C'_x`.
- **The Byzantine assumption moves.** The base assumes less than a third
  Byzantine weight in each configuration. Under Rule 1 that holds for `C'_x`
  if it holds for both `C_x` and `E` (weighted by `C_e`), by the mixture
  bound. `E` drops banned and exited keys, so a coalition's share of `E` can
  be larger than its share of `C_e`. This bound is a model result, not a
  proof of the full protocol.
- **Liveness.** Carried keys that never return are dead weight. Mode `L`
  bounds them below a third. Mode `S` can halt finality again. Then §4.1
  cannot prune them, because pruning needs a quorum.
- **Thin configurations stay a risk in mode `L`.** The keys that kept mining
  still hold more than two thirds. If one operator controls them, that
  operator controls finality until share work refills the configuration.
  `MIN_ENTRIES` counts keys, not operators. A thousand keys under one person
  are not a thousand independent domains (note p. 16).
- **Inclusion capacity.** Carried entries raise `K`, the number of keys
  needed for a quorum. Inclusion takes `ceil(K / 32)` blocks
  (CONSENSUS.md PoWit). A floor that adds many small entries can slow
  finality.
- **Re-entry grinding.** Re-entry is bounded by `prior_k` from configurations
  in force within `REENTRY_LOOKBACK`. A key cannot claim more than it held.
  Exiting and returning does not raise `prior_k`.
- **Post-quantum status.** No new cryptography. Votes keep the base hybrid
  signatures (ML-DSA-65 + Falcon-1024, about 4.6 kB each). A larger
  configuration makes certificates larger in proportion.

## Deployment prerequisites

- An owner decision on the carry mode, `FLOOR_NUM / FLOOR_DEN`,
  `MIN_ENTRIES` and `REENTRY_LOOKBACK`.
- The base partition simulator extended with §4.1 pruning and with these
  rules, and the scenarios above rerun.
- A reference model with exact integer recipes and vectors.
- A clarification in the base of how §4.1 counts presence across a handoff
  that skips epochs.
