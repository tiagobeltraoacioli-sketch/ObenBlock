## Abstract

In the base, every finality vote must be carried inside a block body, and a
block holds at most 32 attestations (CONSENSUS.md "PoWit"). This OBIP lets a
block commit to a batch of votes by reference instead. The votes travel
outside the body, and nodes rebuild the batch from their PoWit pool or fetch
the missing ones. A block that references a batch is valid only when the
node holds every vote in it and every vote verifies. This availability rule
works like the rule for a missing block body. The fixed limit on how many
votes a block may hold is replaced by a byte budget and a verification
budget. Vote semantics, weights and the PoCI rules (DESIGN-obenblock-poci.md)
stay the same.

## Motivation

- **Inclusion bound.** Base parameters are 32 attestations per block and a
  checkpoint every 60 blocks. If `K` is the smallest number of keys that
  reaches the strict quorum of a configuration, the votes for one link need
  at least `ceil(K/32)` blocks to be included. At `K = 1,920` that is 60
  blocks, a whole checkpoint interval. That bound is about inclusion
  capacity. It is not a finality benchmark (technical note p. 19, [R3]).
- **Wider witness sets.** PoCI counts every eligible key, without the old
  64-key cap. A broad, decentralized witness set is the intended outcome, and
  that makes this bound real.
- **What must not be done.** The note warns: "Do not fix the lack of capacity
  by downgrading the weight of whoever was censored or did not fit in the
  block." PoCI already forbids weight changes from absence. The fix must be
  more capacity, not less weight.
- **Duplicate traffic.** Votes are already gossiped one by one as
  `NewPowitItem`. Repeating every vote in every block body that includes it
  sends the same bytes twice.

## Specification

All encodings below are proposals. Exact byte layouts are OPEN until a
reference model exists.

### Vote batch reference (block body item)

```text
vote_batch_ref = u8(version = 1)
               ‖ config_id[32]
               ‖ u64le(source.height) ‖ source.hash[32]
               ‖ u64le(target.height) ‖ target.hash[32]
               ‖ u32le(n)
               ‖ batch_root[32]

vote_id(a)  = SHA-256d("OBB-POCI-v1/vote" ‖ attestation wire bytes)
batch_root  = merkle_root over leaves (key_id[20] ‖ vote_id[32]), strictly ascending by key_id,
              using the PoCI tagged-tree shape (DESIGN-obenblock-poci.md §2) with tags
              "OBB-OBIP5-v1/leaf", "OBB-OBIP5-v1/node", "OBB-OBIP5-v1/root" (count on top)
```

- The body commitment covers each reference, so the block's proof of work
  binds it. OPEN: the exact field, following how the base commits the PoWit
  section.
- Each vote in a batch is an ordinary attestation with the `msg_v3` of
  DESIGN-obenblock-poci.md §2. Its wire form is unchanged: KES public key
  `(depth, root)`, link, and signature.

### Block validity

A block with a vote batch reference is valid only if all of these hold:

1. **Availability.** The node holds all `n` votes the reference names, with
   their bytes, and their leaves rebuild `batch_root`.
2. **Verification.** Every vote passes the base attestation checks under the
   named configuration:
   - membership in `C`;
   - the signature over `msg_v3`;
   - the target is a checkpoint slot;
   - inclusion within `vote_ttl` of the target, measured at this block's
     height.
3. **No double counting.**
   - No key in the batch has already been counted for the same link on the
     block's selected chain, whether in the body, in an earlier batch, or
     twice in this batch.
   - OPEN: whether a repeated key makes the block invalid (strict, proposed
     here) or is simply ignored (lenient).
4. **Budgets.** The block's references together stay within:
   - `MAX_BATCH_VOTES_PER_BLOCK` (OPEN);
   - `MAX_BATCH_BYTES_PER_BLOCK`, counted over the vote bytes even though
     they travel outside the body (OPEN).
   Body attestations keep their own limit of 32. OPEN: whether that limit
   remains or is folded into the new budgets.

Votes in a batch count for justification and finality exactly like body
attestations. Each key counts once per link, with the registry weight of the
named configuration. The strict quorum of DESIGN-obenblock-poci.md §3 applies
unchanged.

### Availability rule

- Until every vote of every reference is held and verified, the block is
  **pending data**. A pending block is:
  - not stored as valid;
  - not relayed;
  - not counted in fork choice;
  - not a parent for templates.
  This is the state of a block whose body has not arrived. It is **not**
  marked invalid, because a later fetch can complete it.
- **Reconstruction.**
  - The node first matches `(key_id, vote_id)` leaves against its PoWit pool.
  - It requests the votes it lacks with `getbatchvotes(block_id,
    ref_index, [leaf_index…])`. This is a new Peer Services message.
  - The peers it asks must have relayed the block. They must answer with the
    votes or with "not held".
- **Pending timeout.** OPEN: how long a node keeps a pending block and
  retries before dropping it. Dropping it is local. A later announcement can
  start the fetch again.
- **Relay.** A node relays a block with references only after the block is
  fully valid. The miner that built it holds all its votes, so honest
  propagation always works.

### Producers

- Any miner may build a batch from its pool. No aggregator role exists in
  consensus, and no aggregator can prevent another miner from including the
  same votes.
- Templates prefer votes that move a link toward quorum. This choice is
  node-local, as in the base ("heaviest first").

### Retention and evidence

- Votes referenced by a block are part of that block's data:
  - archival nodes store them with the body;
  - `getfinalitycertificate` assembles the PoCI §6 certificate from body
    attestations and batch votes.
- **Pruning.** A pruning node keeps referenced votes at least as long as they
  can serve as Proof of Corruption, meaning the key is still provable under
  the base rules. OPEN: the exact retention bound, in epochs.
- Batch votes are attestations. They are valid inputs to double-vote and
  surround-vote evidence (DESIGN-obenblock-poci.md §5).

### Parameters

Each of these is OPEN until measured on regtest:
- `MAX_BATCH_VOTES_PER_BLOCK`;
- `MAX_BATCH_BYTES_PER_BLOCK`;
- `MAX_BATCH_REFS_PER_BLOCK`;
- the pending timeout;
- the pruning retention.

They enter `params_digest`. The base digest has a fixed 110-byte layout, so
this needs a new digest version. A configuration that comes into force under
this OBIP therefore has a different `config_id`.

## Rationale

- **References rather than a monolithic certificate.** A miner could carry
  the full PoCI §6 certificate wire instead. Votes already gossiped would
  then be sent again inside it, and no partial progress would be possible
  before quorum. References to pooled votes give the "send references,
  preserve the authentication" model of the technical note (p. 12). A hash
  alone never counts as a vote: every vote's bytes and signature must be
  held and checked.
- **A raised count limit rather than out-of-body votes.** Simply raising 32
  to a larger number keeps the duplicate traffic. It also ties block size to
  vote volume. It is the fallback if reconstruction proves fragile. OPEN:
  whether this OBIP should be reduced to that.
- **A succinct aggregate proof rather than signatures.**
  - A pairing SNARK (Groth16) or BLS aggregation would be compact, but it is
    **not post-quantum**.
  - A STARK of the batch would be post-quantum under hash assumptions, but it
    is tens to hundreds of kB and has not been measured for this relation.
  - This is P1/P2 research in the technical note. OBIP-2 specifies compact
    certificates outside consensus; using them in place of included votes
    would be a later OBIP.
  This OBIP keeps every signature, so no new proof system enters consensus.
- **A random multi-round committee.** Sampling a smaller voter set to fit
  the limit swaps a guarantee over all the weight for a guarantee over a
  sample. Each round also gives an attacker a new chance. The note's binomial
  example, with 25 % adversarial weight, gives:
  - `P(X >= k/3)` of about 2.8 % for 100 seats;
  - `1.7 × 10^-9` for 1,000 seats.
  The base rejects this, and so does this OBIP.
- **A local committee change.** Choosing as voters whoever answers first is
  rejected for the same reasons as in the base: it favours fast networks and
  split identities, and it is a different consensus regime.
- **A stake bond for aggregators** is rejected. The base has no stake, and an
  aggregator here has no power that would need a bond.

## Backwards Compatibility

- This is a hard fork. Blocks with vote batch references are invalid under
  the base rules.
- Activation is a coordinated ObenBlock release height. It should be the
  opening checkpoint of an epoch, so the new parameter digest takes effect
  at a handoff. OPEN: how the handoff to the first configuration with the new
  digest is triggered.
- GnB is unaffected.

## Security Considerations

- **Data withholding.** A miner can publish a block that references votes it
  withholds. Honest nodes keep such a block pending and never build on it.
  The miner wastes its block. Finality is not harmed, because withholding
  votes is the same as not including them. A miner that withholds from some
  peers only can delay those peers. The pending timeout and fetching from
  several peers bound the delay, and the exact bound is OPEN.
- **Verification denial of service.**
  - Each vote costs one KES check with a hybrid ML-DSA-65 + Falcon-1024
    signature.
  - A peer can make a node check votes only after a header with valid proof
    of work that commits to them. This is the same argument as for witness
    shares in the base.
  - Verified votes are cached by `vote_id`.
- **Bytes.** One hybrid signature is about 4.6 kB before the KES path. At
  `K = 1,920` the votes for one link are about 8.8 MB or more. Out-of-body
  transport removes the count limit and the duplicate relay. It does not
  remove the bytes, and the budgets must keep a full node verifying in real
  time on reference hardware.
- **Censorship.** Miners can still refuse to reference a key's vote. More
  capacity makes censorship a choice rather than a capacity effect. It does
  not stop it. Absence is still never punished.
- **Assumptions.**
  - Less than 1/3 of the configuration's weight is Byzantine.
  - Some honest miners are online, so votes are eventually referenced.
  - Peers that relayed a block serve its votes.
- **Post-quantum status.** No change to the base: every vote keeps its
  post-quantum signature. Pairing SNARKs, BLS and Groth16 are not
  post-quantum and are not used.

## Deployment prerequisites

- Regtest measurements published:
  - block propagation with references against full bodies;
  - reconstruction hit rate;
  - verification time per block, p50/p95/p99, at the proposed budgets;
  - finality latency at `K` of 64, 640, 1,920 and above.
- A reference model next to `reference/poci_reference.py` (branch `obenblock/o11a-poci-reference`), with vectors.
- The new `params_digest` version specified.
