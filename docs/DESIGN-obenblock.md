# ObenBlock relaunch: SHA-256d + PoWit

Status: design, 2026-10-17. Owner decisions recorded below. Implementation is
split into the packages at the end; nothing here is active yet.

ObenBlock (ticker **OBB**, site **obenblock.xyz**) is a relaunch of this code
base as a new chain with a clean genesis. The GnB chain is not changed by
it. Blocks are mined with **SHA-256d** on Bitcoin ASICs. Finality comes
from **PoWit** witness votes weighted by share work. The finalized
checkpoints are anchored in **Bloch**.

## 2. Chain identity

- **Chain id** (folded into every sighash and PoWit message):
  - mainnet `0x4F42_0001` ("OB");
  - regtest `0x4F42_0002`;
  - GnB's `0x474E_000x` stay GnB's.
  So no transaction, attestation or share is valid on both chains.
- **Addresses**: human-readable part `obb`: `obb1q…` for a key hash and `obb1m…` for
  a spend policy (regtest: `obb1t…`, `obb1n…`).
  - **gnb compatibility**: `gnb1q…`/`gnb1m…` strings, and the `bloch1q…` ones
    GnB already accepts, are parsed as the same 20- or 33-byte script and
    shown back as `obb1…` (`address::normalize_legacy_address`).
  - A GnB keystore (v2/v3) opens unchanged: the v3 associated data binds the
    address string stored in the file, so it is checked against that string,
    then normalized.
  - The same key controls its coins on both chains; the chain id keeps the
    signatures apart.
- **P2P**:
  - protocol id `/obenblock/pq/1.0.0`;
  - default ports 18110 (P2P) and 18210 (RPC), so a host can run both chains;
  - DNS seed `seed.obenblock.xyz`.
- **Binaries**: `obenblock` (node), `obenblock-cli`, `obenblock-wallet`.
  Internal crate names (`gnb-crypto`, `gnb-smh`, …) are renamed in a later,
  mechanical step.
- **Domain-separation tags** (`GNB-TXSIG-v3`, `GNB-POWIT-v2/attest`,
  `GNB-POLICY-v1`, …) are protocol constants and stay as they are. The chain id
  already separates the chains, and renaming them would only rewrite every
  vector. They are documented as historical names.

## 3. Genesis and rules from height 0

- Every rule of both hardening activations applies from the genesis block:
  - first and second hardening heights 0;
  - PoWit from height 0 (the witness set is empty for the first two epochs);
  - version-3 transactions, sighash v3, canonical witnesses;
  - the H2 PoWit rules (uncapped W from finalized history, v2 messages);
  - PF-4;
  - the conservative suite 0x0003.
  None of the legacy regimes is reachable on ObenBlock. The code keeps them
  for GnB.
- **Allocations**: the four allocations of the tokenomics stay as they are:
  9.0M mined, 1.0M carry-over, 1.25M team, 1.25M founder, so the supply is
  12,500,000 OBB (owner, 2026-10-17).
- **Carry-over: as in GnB today** (owner, 2026-10-17). The genesis pays the
  1.0M carry-over allocation exactly as GnB's genesis does:
  - the same Bloch Genesis-3 snapshot (`genesis/`);
  - the same fixed conversion
    (`floor(v × CARRYOVER_ALLOCATION_SAT / CARRYOVER_SOURCE_TOTAL_SAT)`);
  - the same outputs to the same 20-byte key hashes.
  A holder opens the same JSON keystore they use for Bloch and GnB today
  (`bloch1…`/`gnb1…` addresses, normalized to `obb1…`, §2) and spends on
  ObenBlock with the same key.
  Nothing mined or moved on the GnB chain is carried: GnB's later history
  does not exist on ObenBlock.
- `MIN_CHAIN_WORK` is 0, and there is no release finality checkpoint or
  assumed-valid block at launch. Each release sets them from independent nodes
  (`tools/release/min_chain_work.py`).

## 4. Proof of work: SHA-256d, ASIC compatible

### 4.1 The 80-byte PoW header

```text
pow_header = u32le(version)                                   4
           ‖ parents_commitment                               32
           ‖ merkle_root                                      32
           ‖ u32le(time)                                      4
           ‖ u32le(bits)                                      4
           ‖ u32le(nonce)                                     4   = 80 bytes

parents_commitment = SHA-256d("OBB-PARENTS-v1" ‖ u32le(n) ‖ parent_0 ‖ … ‖ parent_{n-1})
block_id           = SHA-256d(pow_header)
valid PoW         <=> block_id, read as a 256-bit little-endian integer, <= target(bits)
```

- This is Bitcoin's header layout. An unmodified SHA-256d ASIC and its
  stratum firmware mine it:
  - the 32-bit nonce;
  - version rolling (BIP 320: bits 13–28 of `version` are free, the other
    bits must equal the block version);
  - an extranonce in the coinbase changes `merkle_root`.
- The full parent list travels with the header. A block is valid only if
  its list hashes to `parents_commitment` (sorted ascending, no duplicates,
  at most `MAX_PARENTS`).
- `time` is u32: seconds until 2106. The MTP rule and `MAX_FUTURE_SECS`
  (600) stay.
- The block id is the PoW hash (Bitcoin's convention). GhostDAG's tie-breaks
  by hash use it.
- Height and blue score are still not committed by the id. They are derived
  (docs/CONSENSUS.md).

### 4.2 Work, difficulty and the pow limit

- `work(B) = floor(2^256 / (target(B.bits) + 1))`, Bitcoin's chain work. The
  GnB-SMH shift (`POW_V3_DIFFICULTY_SHIFT`) does not apply.
- ASERT as today (`gnb_smh::difficulty`, half-life 2 h, 30 s blocks),
  anchored at the genesis block.
- `pow_limit` = Bitcoin's `0x1d00ffff`.
- **Launch difficulty** (owner: "the best technique"). Two mechanisms make a
  wrong guess harmless in either direction, so no exact hashrate estimate is
  needed:
  - **Start high.** The genesis target corresponds to 1 EH/s of SHA-256d
    (`LAUNCH_HASHRATE`, a constant set at launch). If the real hashrate is
    lower, the stall relief (§5.1) brings the target down in hours instead of
    letting blocks stall. At 1 PH/s, the first block comes after about 6 h,
    and blocks are back to schedule within about a day.
  - **Slow start** (Zcash's technique against an "instamine"). The block
    subsidy ramps linearly from 0 to its full value over the first 5,760
    blocks (about 2 days): `subsidy(h) = full × min(1, h / 5,760)`. If the
    real hashrate is higher than the estimate, the early blocks still arrive
    too fast while ASERT catches up, but they pay almost nothing. The
    withheld subsidy (about 3,080 OBB) is never issued; the supply cap stays
    an upper bound.

## 5. Liveness: hashrate that arrives and leaves

A miner can bring a large amount of SHA-256 hashrate, raise the difficulty and
leave. Two criteria make sure neither block production nor finality stalls.

### 5.1 Stall relief (block production)

ASERT computes the target of B from its selected parent and is fixed while B is
being mined. If most of the hashrate leaves, the next block at that target can
take hours. On top of ASERT, B's own timestamp relaxes B's target once B is
late:

```text
late(B)        = max(0, B.time - sp(B).time - 6 * T)              T = 30 s
target_eff(B)  = min(pow_limit, target_asert(B) * 2^(floor(late(B) / 60) * 60 / H_r))
                                                                  H_r = 1,800 s
expected_bits(B) = canonical bits of target_eff(B)
```

- In words: after 3 minutes without a block, the target doubles every 30
  minutes, in 60-second steps.
- The steps let a pool hand out one job per step. Within a step, `ntime`
  rolling does not change `bits`.
- **Bound**: with a fraction `r` of the old hashrate left, the next block is
  expected after about `3 min + 30 min × log2(1/r)`:
  - 10 % left: about 1 h 45 min worst case, typically minutes;
  - 0.1 % left: about 5 h.
  ASERT then adjusts the following blocks from B's late timestamp.
- **Abuse bound**: a miner may claim at most `MAX_FUTURE_SECS` (600 s) of
  extra lateness, which is `2^(600/1800)` ≈ 1.26× easier, and only for a
  block whose parent is already 3 minutes old. ASERT pulls the next blocks
  back.

### 5.2 Faster inactivity leak (finality)

When no checkpoint finalizes for `leak_after_epochs` (4 epochs, 24 h), every
member of W whose votes were not included in an epoch loses **half** of its
weight for that epoch (GnB: 1/16). If a fraction `a` of the witness weight
disappears, finality resumes after `24 h + 6 h × ceil(log2(2a/(1-a)))`:

| Weight that left | Finality back after |
| --- | --- |
| 50 % | about 30 h |
| 90 % | about 54 h |
| 99 % | about 72 h |

- Blocks never stop meanwhile. Only finality waits.
- A clean exit is immediate. A witness may publish an **exit** message signed
  with its KES key, and its weight leaves W from the next epoch.
- Caveat, as for every finality gadget with a leak: a network partition that
  lasts more than about 30 h can finalize on both sides. Nodes then keep the
  finality they reached, raise the conflict alert (`getfinalityinfo`), and the
  operator decides (package A2: finality is sticky, and `ignorefinalized` /
  `setfinalitycheckpoint` are the escape hatch).

## 6. PoWit on SHA-256d

### 6.1 Witness shares

A share proves that its miner holds the attested block's data. The proof is a
SHA-256d header an ASIC can mine. The custody sampling moves from every
nonce to every **job**:

```text
job_commitment = SHA-256d("OBB-WSHARE-v1/job" ‖ attested ‖ witness ‖ SHA-256d(payout)
                          ‖ u64le(job_nonce) ‖ chunk[idx_0] ‖ … ‖ chunk[idx_7])
idx_k          = from SHA-256d("OBB-WSHARE-v1/idx" ‖ attested ‖ SHA-256d(payout) ‖ u64le(job_nonce) ‖ u8(k))
share_header   = u32le(version) ‖ attested ‖ job_commitment ‖ u32le(time) ‖ u32le(bits) ‖ u32le(nonce)
valid         <=> SHA-256d(share_header) <= target(bits) × SHARE_TARGET_FACTOR (16)
```

- An ASIC exhausts the 32-bit nonce of one job in milliseconds. Every new
  job needs eight fresh 64-byte chunks of the attested block's transaction
  stream, so the job server must hold the block. Custody is enforced at the
  operator, not per nonce.
- Verification costs one SHA-256d and the chunk reads: about 1 µs instead of
  about 90 ms for GnB-SMH. This removes the CPU-cost part of package A3 and
  the share-verification cost of initial sync (package G).
- Rewards, slots, the window and the inclusion bonus are unchanged
  (`docs/DESIGN-witness-shares.md`).

### 6.2 Witness weight: share work, long window

- The weight is share work only (owner decision), uncapped, from finalized
  history (the H2 rules, from genesis).
- **Window: 112 epochs = 28 days** (GnB: 28 epochs = 7 days), with 6-hour
  epochs of 720 blocks. To own 2/3 of W, an attacker who rents hashrate must
  out-mine the honest share work for about four weeks, not one hour. Even
  then it cannot revert checkpoints that are already final; it can only
  steer finality from then on.
- Cost: the PoWit state keeps `window + 2` epochs of share work per key.
  Package A3 stores it per epoch with per-block diffs.

## 7. Reorg protection, together

| Layer | What it stops |
| --- | --- |
| Finality pin, sticky (A2) | no reorg below a checkpoint the node finalized; a conflicting finalization raises an alert and waits for the operator |
| W from finalized history + 28-day window | a private fork cannot mint its own witness set; capturing W costs four weeks of majority share work |
| Minimum chain work + release finality checkpoint + assumed-valid | a syncing node is not captured by a cheap chain |
| Bloch anchoring (§8) | a checkpoint published in Bloch cannot be contradicted without also attacking Bloch |
| Confirmation by finality | wallets and exchanges credit at "finalized" (`getfinalityinfo`), not at N blocks |
| Deep-reorg alerts | logged and counted (`gnb_deep_reorgs_total`), never silent |

## 8. Anchoring in Bloch

The other direction already exists: `docs/BLOCH-ANCHOR.md` (PR #20)
records Bloch's finalized checkpoints in ordinary transactions of this chain.
That protects Bloch history with this chain's proof of work. The anchors
below protect ObenBlock history with Bloch's finality. Together they make
mutual anchoring. **Both directions are used** (owner, 2026-10-17).

- **What**: for every finalized checkpoint that starts a new epoch (one every
  6 h), an anchor record:
  `chain_id ‖ slot ‖ block_id ‖ finalized_at ‖ W-digest`.
  `W-digest` is SHA-256d of the sorted (key, weight) set that finalized it.
- **Publication**: by any operator with a Bloch account (a reference
  `obenblock-anchor` daemon), as a Bloch transaction to the anchor
  registry. The first record for a slot wins on Bloch; a conflicting one is
  evidence.
- **Use, phase 1 (node-local)**:
  - a node started with `--bloch-rpc URL` reads the anchors that its own
    Bloch node has finalized;
  - it treats the newest one as its weak-subjectivity anchor
    (`setfinalitycheckpoint`, automatic);
  - it refuses any chain that contradicts it.
  This is the same trust model as the bridge signers (docs/SIDECHAIN-BLOCH.md:
  "each signer reads … from its own follower").
- **Phase 2**: a Bloch light client in the node (header sync of Bloch
  finality), removing the trusted Bloch RPC.
- **Bloch side**: the anchor registry needs the Bloch code base. The record
  format above is the interface. *Pending access to the Bloch repository.*
