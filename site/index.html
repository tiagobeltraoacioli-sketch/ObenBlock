One hash. Two passes.

Bitcoin's header layout: an unmodified SHA-256d ASIC and its stratum firmware mine it, with the 32-bit nonce, version rolling (BIP 320) and an extranonce in the coinbase. A commitment to the parent list ties the header to the BlockDAG. The block id is the proof-of-work hash.

NO MERGED MINING · ASERT, 2 H HALF-LIFE · STALL RELIEF

Work has a memory too.

Witness weight is share work recorded in finalized history, with no stake. Each new share job needs fresh chunks of the attested block, so whoever runs the job server must hold the block. To own two thirds of the weight, an attacker must out-mine the honest share work for about four weeks.

Two networks. Connected histories.

Every six hours, the finalized checkpoint that starts a new epoch is recorded in Bloch. A node started with a Bloch RPC reads the anchors its own Bloch node has finalized and refuses any chain that contradicts the newest one. A Bloch light client in the node comes in a later phase.

02 / THE TECHNICAL FOUNDATION

Open on the outside.
Rigorous on the inside.

The GnB code base brings a BlockDAG, adaptive difficulty and hybrid post-quantum signatures. ObenBlock carries this architecture over to SHA-256d work, with every hardening rule in force from the genesis block.

DEFAULTML-DSA-65+FALCON-1024
OPTIONALSLH-DSA-128s+FALCON-1024

Post-quantum protection belongs to the signature layer: both halves of every signature must verify. Mining uses SHA-256d. Full cryptographic specification.

03 / CRYPTOGRAPHY

Two signatures.
Both must verify.

Every key pairs two post-quantum schemes, and a forgery has to break both. Below are the two signature suites and every hash, key and channel that protects a coin.

SUITE 0x0001DEFAULT

ML-DSA-65 + Falcon-1024

Two lattice schemes of different constructions: ML-DSA (NIST FIPS 204, Module-LWE) and Falcon (NTRU lattices). Wallets use it by default.

NIST security level
3 (ML-DSA-65) and 5 (Falcon-1024)
Public key
3,745 bytes
Signature
Up to 4,775 bytes
Used for
Transactions and spend policies, PoWit witness keys, node identity and signed messages
SUITE 0x0003OPTIONAL · CONSERVATIVE

SLH-DSA-128s + Falcon-1024

A hash-based scheme, SLH-DSA-SHAKE-128s (NIST FIPS 205, secure as long as SHAKE256 is), paired with Falcon. A forgery needs a break of a hash function and of a lattice problem.

NIST security level
1 (SLH-DSA-128s) and 5 (Falcon-1024)
Public key
1,829 bytes
Signature
Up to 9,322 bytes, about 7× slower to verify
Used for
Transaction signatures only: key addresses and spend-policy keys, valid from the genesis block

How the halves are bound. Each half signs its own message, which names the suite and the half and carries the transaction's signature hash. A key of one suite never verifies a signature of another, and a signature with one half removed never verifies. Wallet support. The command-line wallet creates keys of either suite; the browser wallet, PQ-PSBT and descriptors use the default suite for now. Legacy. ML-DSA-65 alone (suite 0x0002) stays valid only so that outputs locked to such keys remain spendable. It is non-standard, and wallets never sign with it.

A clean genesis. The same carry-over keys.

The genesis pays the carry-over exactly as GnB's genesis does: the same snapshot, the same fixed conversion, to the same 20-byte key hashes. Nothing mined or moved on the GnB chain is carried. 07 / THE NEW CHAPTER

The evolution,
made clear.

What changes with ObenBlock, and what carries over from GnB.

Is ObenBlock live yet?

Not yet. The specification of 17 October 2026 is being implemented in packages. The genesis block hash, the DNS seed, the release binaries and the launch date are published at launch, on this site and in the repository. Until then there is no ObenBlock network to connect to.

Is ObenBlock GnB's new name?

The GnB repository was renamed ObenBlock and keeps its history. ObenBlock itself is a new chain: a clean genesis, the OBB ticker and SHA-256d mining. The relaunch does not change the GnB chain.

Are my GnB and Bloch keys still valid?

Yes. A GnB keystore (v2 or v3) or the Bloch keystore you use today opens unchanged, and gnb1… and bloch1… addresses are read as the same script and shown as obb1…. The same key controls its coins on both chains; the chain id keeps the signatures apart. The carry-over is paid to the same key hashes as in GnB's genesis; balances from GnB's later history are not carried.

Can I mine ObenBlock with a Bitcoin ASIC?

That is the design: the block header is Bitcoin's 80-byte layout, so an unmodified SHA-256d ASIC and its stratum firmware mine it, with the 32-bit nonce, version rolling and an extranonce in the coinbase. There is no merged mining. The miner and getblocktemplate ship with the release.

Do SHA-256d and PoWit do the same thing?

They serve different functions. SHA-256d is the proof of work used to mine blocks. PoWit is the finality layer: witnesses vote with weight earned from work shares, using keys that evolve each epoch. Wallets and exchanges credit a payment once it is finalized, not after a fixed number of blocks.

Which post-quantum signatures does ObenBlock use?

By default, ML-DSA-65 + Falcon-1024: every signature carries both, and both must verify. For transaction signatures, a holder can choose the conservative suite instead, SLH-DSA-128s + Falcon-1024, which adds a hash-based guarantee at about twice the signature size. Witness keys, node identities and signed messages always use the default suite. SHA-256d is the mining hash, not a signature.

Is there a testnet?

No public testnet. ObenBlock has one mainnet and a regtest network for local development and tests.
