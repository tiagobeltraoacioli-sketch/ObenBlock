One hash. Two passes.

Bitcoin's header layout, byte for byte, with a commitment to the parent list in place of the previous block hash: the 32-bit nonce, version rolling (BIP 320) and a rollable time. The block id is the proof-of-work hash. The node serves pools through getblocktemplate and submitblock.

Work has a memory too.

Witness weight is share work recorded in finalized history, with no stake, over a 28-day window. Each new share job needs fresh chunks of the attested block, so whoever runs the job server must hold the block. The specified growth cap bounds how fast the weight can change: renewals first, then at most 1/64 of the total per epoch. Capturing two thirds then takes at least about 18 days of visible growth, whatever the hashrate rented.

Two networks. Connected histories.

Bloch's finalized checkpoints are recorded in ObenBlock transactions, and the first finalized checkpoint of each ObenBlock epoch, one every six hours, is recorded in Bloch. PoCI · PROOF OF CORRUPTION OR INTEGRITY

From the genesis

Every finality decision ends in one of two verifiable objects: a finality certificate, or evidence that a key signed two votes the rules forbid. Nothing else changes the weight of a decision: no absence, timeout, partition or local clock.

01

Frozen configuration

Each epoch's voter registry, its keys, weights and total, is fixed under a config_id that every vote names. A vote counts only with the registry's weight.

02

Strictly more than 2/3

3 × voted > 2 × total. Two quorums of one configuration overlap in more than a third, so with under a third Byzantine weight they share an honest key.

03

Handoff

The next configuration enters into force only when the checkpoint that opens its epoch is finalized under the current one. Exits, bans and expiring weight wait for that handoff.

04

Absence pruning by the old committee

A key with no included votes in the 4 epochs (24 h) before a handoff is left out of the next configuration, but only when keys holding more than two thirds of the current one were present: a stall is not absence. It returns with a KES-signed rejoin message, under the growth cap.

05

Proof of Corruption

A double or surround vote by one key under one configuration is evidence. The key is excluded for 100 epochs, about 25 days. Absence, slowness or a vote for a losing branch are never punished.

06

Finality certificate

The proof of integrity: configuration, link and signatures worth more than two thirds of it, checked against the registry. Nodes keep one for every finalized checkpoint.

Without a quorum, blocks keep coming and finality halts until more than two thirds of the configuration vote again; recovery is a coordinated, explicit act, never automatic. Without stake, exclusion and the lost share rewards are the whole penalty: PoCI makes corruption detectable and attributable. PoCI is in force from height 3,600, after a launch buried under one epoch of proof of work. Read the PoCI design.

03 / ANCHORING

Two chains.
Anchored both ways.

Each chain records the other's finalized checkpoints. Neither direction is a consensus rule, and no anchor overrides a node's own finality.

BLOCH → OBENBLOCKBLA1 ANCHORS

Bloch checkpoints in ObenBlock

An anchoring wallet records Bloch's finalized checkpoint (epoch, root, height) in an ordinary ObenBlock transaction, with two unspendable marker outputs. Buried under SHA-256d work, it turns a rewrite of Bloch history behind it into a contradiction of a public, timestamped record.

Version 1: a 33-byte root marker and a 20-byte BLA1 epoch and height marker, 546 base units each

OBENBLOCK → BLOCHADVISORY

ObenBlock checkpoints in Bloch

One 84-byte record per epoch, every six hours: chain id, slot, block id, finalization time and a digest of the witness set that finalized it. A node started with --bloch-rpc reads the records its own Bloch node has finalized. By the specification, a contradicting anchor raises the finality alert and the operator decides; an agreeing one is reported as corroboration.

05 / CRYPTOGRAPHY

Two signatures.
Both must verify.

Every key pairs two post-quantum schemes, and a forgery has to break both. Below are the two signature suites and every hash, key and channel that protects a coin.

SUITE 0x0001DEFAULT

ML-DSA-65 + Falcon-1024

Two lattice schemes of different constructions: ML-DSA (NIST FIPS 204, Module-LWE) and Falcon (NTRU lattices). Wallets use it by default.

NIST security level
3 (ML-DSA-65) and 5 (Falcon-1024)
Public key
3,745 bytes
Signature
Up to 4,775 bytes
Used for
Transactions and spend policies, PoWit witness keys, node identity and signed messages
SUITE 0x0003OPTIONAL · CONSERVATIVE

SLH-DSA-128s + Falcon-1024

A hash-based scheme, SLH-DSA-SHAKE-128s (NIST FIPS 205, secure as long as SHAKE256 is), paired with Falcon. A forgery needs a break of a hash function and of a lattice problem.

NIST security level
1 (SLH-DSA-128s) and 5 (Falcon-1024)
Public key
1,829 bytes
Signature
Up to 9,322 bytes, about 7× slower to verify
Used for
Transaction signatures only: key addresses and spend-policy keys, valid from the genesis block

How the halves are bound. Each half signs its own message, which names the suite and the half and carries the transaction's signature hash. A key of one suite never verifies a signature of another, and a signature with one half removed never verifies. Wallet support. The command-line wallet creates keys of either suite; the browser wallet, PQ-PSBT and descriptors use the default suite for now. Legacy. ML-DSA-65 alone (suite 0x0002) stays valid only so that outputs locked to such keys remain spendable. It is non-standard, and wallets never sign with it.

06 / THE ECONOMICS

A clear cap.
From the very first block.

ObenBlock keeps the four allocations of the GnB tokenomics, scaled to a 1,000,000 OBB cap. Capped emission, halvings, vesting and fees written in code: every transfer pays 1% of the amount sent (change is exempt), split like the block subsidy between the miner (80%) and the PoWit witnesses (20%).

A clean genesis. The same carry-over keys.

The genesis pays the carry-over exactly as GnB's genesis does: the same snapshot, a fixed proportional conversion, to the same 20-byte key hashes. Nothing mined or moved on the GnB chain is carried. The block subsidy ramps up linearly over the first 5,760 blocks (about two days); the subsidy withheld, about 246 OBB, is never issued.

10 / THE NEW CHAPTER

The evolution,
made clear.

What changes with ObenBlock, and what carries over from GnB.

Is ObenBlock live yet?

Not yet. The mainnet launch is being prepared. The launch time, the genesis block hash, the seed nodes, the stratum endpoint and the release binaries are published at launch, in the launch status above and in the repository. Until then there is no ObenBlock network to connect to.

Is ObenBlock GnB's new name?

The GnB repository was renamed ObenBlock and keeps its history. ObenBlock itself is a new chain: a clean genesis, the OBB ticker and SHA-256d mining. The relaunch does not change the GnB chain.

What is PoCI, and when does it start?

PoCI (Proof of Corruption or Integrity) is a strict finality profile for ObenBlock: a frozen configuration per epoch, a quorum of strictly more than two thirds, a handoff between configurations, absence pruning authorized by the old committee, a 100-epoch exclusion on proven equivocation and a finality certificate. It is in the node from the genesis. The first 3,600 blocks (4 epochs plus one epoch of burial) are proof of work only; strict finality starts there.

Can rented hashrate take over finality?

Weight comes from share work in finalized history over a 28-day window, so a burst of hashrate does not buy instant weight, and checkpoints already final stay final. The growth cap in the node goes further: whatever the rented hashrate, reaching two thirds of the weight takes at least 71 epochs, about 18 days, visible the whole time.

Are my GnB and Bloch keys still valid?

Yes. A GnB keystore (v2 or v3) or the Bloch keystore you use today opens unchanged, and gnb1… and bloch1… addresses are read as the same script and shown as obb1…. The same key controls its coins on both chains; the chain id keeps the signatures apart. The carry-over is paid to the same key hashes as in GnB's genesis; balances from GnB's later history are not carried.

Can I mine ObenBlock with a Bitcoin ASIC?

The block header is Bitcoin's 80-byte layout, so SHA-256d ASICs do the work, with the 32-bit nonce, version rolling and a rollable time. The node serves pools through getblocktemplate and submitblock; the stratum endpoint for ASICs is published at launch. There is no merged mining.

Do Bloch anchors decide which chain is final?

No. An anchor is evidence, not a vote: a record carries no proof that the witness set finalized it, and anyone with a Bloch account can publish one. By the specification, a node that sees an anchor contradict its own finality raises an alert and the operator decides. Anchors that carry a verified finality certificate are a proposal (OBIP-3).

Do SHA-256d and PoWit do the same thing?

They serve different functions. SHA-256d is the proof of work used to mine blocks. PoWit is the finality layer: witnesses vote with weight earned from work shares, using keys that evolve each epoch. Wallets and exchanges credit a payment once it is finalized, not after a fixed number of blocks.

Which post-quantum signatures does ObenBlock use?

By default, ML-DSA-65 + Falcon-1024: every signature carries both, and both must verify. For transaction signatures, a holder can choose the conservative suite instead, SLH-DSA-128s + Falcon-1024, which adds a hash-based guarantee at about twice the signature size. Witness keys, node identities and signed messages always use the default suite. SHA-256d is the mining hash, not a signature.

Is there a testnet?

No public testnet. ObenBlock has one mainnet and a regtest network for local development and tests.
